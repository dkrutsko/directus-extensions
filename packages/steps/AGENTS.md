# directus-extension-steps

A Directus 11 bundle extension, published on npm as `directus-extension-steps`. It adds the **Steps** interface (`steps`) and the **Steps** display (`steps`) for `string` and `integer` fields which hold one value out of an ordered list. The interface draws the list as a progress track, one button per step, and a click makes a step the current one; the display shows a pip per step and the name of the current one in layouts. It stores what the stock Dropdown stores and exists for fields where the order of the choices carries meaning.

The rules which hold for every extension of this repository (independence, bundle hygiene, code style, releasing, the sandbox) are in the root `AGENTS.md`. This file only holds what is specific to this package; `CLAUDE.md` imports it.

## Commands

Run these in this folder, after `npm install` in the repository root:

```bash
npm run dev        # watch build, unminified
npm run check      # vue-tsc, plus tsc over the tests (tsconfig.test.json)
npm run build      # dist/app.js + dist/api.js
npm test           # vitest
npm run validate   # directus-extension validate
```

`prepublishOnly` runs check, build, test and validate. The build comes before the tests, because `tests/bundle.test.ts` reads `dist/app.js`; without a bundle that one test is skipped with a warning.

## How it works

- **A bundle with an app side only.** The manifest has the two entries and no hook, endpoint or operation. The SDK still writes `dist/api.js`, three empty lists, because a bundle has both paths. The entry names differ (`steps`, `steps-display`), as a bundle needs; the ids are the same, since Directus registers interfaces and displays apart.
- **The options are cleaned once, in `readSteps`.** `choices` is whatever the schema holds. An entry which is not an object, has no value, repeats the value of an earlier entry or, on an integer field, is not a whole number, is left out. An icon which is not a name becomes `null`. Positions count what is kept. The options themselves are never changed, and nothing is reported: the README says which entries are dropped.
- **A step has a name and may have a label.** The name is the trimmed `text`, or the value as text when there is none; it is never empty, and it is what the accessible name, the tooltip and the display go by. The label is what is written under the marker, and it is the text and nothing else: `null` for a step without a text, and for every step when the field's `showLabels` option is off. `readSteps` takes that option as its third argument and `labelsShown` reads it: only the boolean `false` switches the labels off, so a field without the option, which is every field set up before it existed or by the stock Dropdown, shows them. For a while a step could hide its own label with a `showLabel` key; the key is gone, and one which is still stored is ignored like any key an entry may hold. The display calls `readSteps` without the option: it goes by names and has nothing to do with labels.
- **`showLabels` is a boolean prop with a default of `true`** (`withDefaults` in `interface.vue`). Without the default Vue would turn a prop which is not passed into `false`, and every field without the option would lose its labels.
- **A track without a single label is compact** (`isCompact`), which is the case when `showLabels` is off or when no step has a text: the markers alone in a box exactly as high as a stock input. That is arithmetic, not measurement: the track is `--theme--form--field--input--height` less the two borders, and the padding above a marker (`--st-top`) is half of what the marker leaves; the line between two markers takes its height from the same variable. The marker is placed from the top of its button, not centred in it, so it stays on the middle line of the box when the track scrolls and the scrollbar takes the lower edge of the track. The bar is 6px there, which fits under the markers, and the box keeps its height. The focus ring is drawn round the marker in this form, not round the column, whose lower edge would be under the scrollbar. Columns are at least 3rem, a marker and a gap. One label anywhere brings the row of labels back for the whole field.
- **A value is matched by its text, and written in the type of the field.** `storedForm` puts a value into the form the field stores, a safe whole number on `integer` and text on anything else; `keyOf` is that form as text, and steps and stored values are compared by it. So the number `2` finds a step whose option holds `"2"`, and a click on that step writes the number. A field type other than `integer` is treated as text.
- **Two values can never be the same step,** because `readSteps` keeps the first of each key. That is what makes "one current step" true without a check in the template.
- **Choosing the current step does nothing.** `chosen` gives `undefined` and the component returns before it emits, so the form is not marked as changed. The track never writes `null`.
- **An empty field and a field with a foreign value are told apart.** `trackOf` reports the value as `unknown` when it is none of the steps, unless the field holds `null`, nothing, or blank text. The component then names it in a line under the track. Every step is upcoming in both cases. The line is an English sentence and is marked as one (`lang="en" dir="ltr"`), so it reads correctly in a right-to-left page; the value inside it is isolated, since it can be in any script. The value stands between quotation marks and keeps its spaces (`white-space: pre-wrap`): text is matched to the letter, so `"draft "` is not the step `draft`, and without the marks the line would seem to name a step of the field. The list points at the line (`aria-describedby`), so someone who enters the track without seeing it is told why no step is the current one.
- **Labels are text, markers carry the state.** The label of a done and of an upcoming step are both in the text colour of an input (`--theme--form--field--input--foreground`), because an upcoming step is a choice on offer and `--theme--foreground-subdued` is 2.1 to 1 on white in the default light theme. What is quiet about an upcoming step is its marker: the number or icon in the subdued colour, the ring and the line in the border colour of the inputs. Done, current and upcoming differ without colour by a filled marker, a ringed marker with a bold label, and an empty marker. Only a dimmed field has subdued labels, which is what tells a read-only field from an editable one.
- **The box is a stock input in everything but its content.** Border, radius, background, shadow and their hover, focus-within and disabled forms are the form-input tokens. The input's padding is split between the box and the buttons (`--st-inset`), which need room of their own for the focus ring.
- **Equal columns, then a scroll.** The list is a grid with `grid-auto-columns: minmax(4.5rem, 1fr)`, and every item may shrink below its content (`min-inline-size: 0`), so no label widens its column. The line after a step is a pseudo-element of the list item which runs from the edge of its marker to the edge of the next: `inset-inline-start: calc(50% + marker / 2)` and `inline-size: calc(100% - marker)`. It relies on the columns being equal, and being laid out along the inline axis it needs no code for right-to-left. It does not pass under the markers, so a dimmed marker does not show a line through it.
- **The scrollbar is styled so that it shows.** `::-webkit-scrollbar` rules make it a thin bar which is always drawn where the system would otherwise hide scrollbars until they are used; browsers without that pseudo-element get `scrollbar-width` and `scrollbar-color`. The thumb is in `--theme--foreground-subdued`: the border colour of the inputs, which it had at first, is 1.2 to 1 against the box and could be overlooked.
- **The current step is brought into view by moving the track only** (`reveal`), since `scrollIntoView` would move the page too. `revealOffset` says how far, in either writing direction, and there are two ways.
  - A step which was chosen with the pointer stays under the pointer: the track moves no further than it takes to show the step whole, which is not at all for a step that already is. Were it brought to the middle, the second click of a double click would land on a neighbour and choose it. `choose` remembers the key of such a step (`pointed`); a click made with Enter or Space has a `detail` of 0, which is how the two are told apart.
  - Any other current step goes to the middle of what shows: on load, when the value changes from outside, after a choice with the keyboard, and when the width of the track changes (a `ResizeObserver`, whose first call is the track being laid out). A change of the track's height alone, which is a label taking a second line, moves nothing.
  - The track moves once per step (`shown` holds the key it last moved for). The form hands over `null` for a moment around a save and then the same value again; that is no new step, and the track stays where the user left it.
  - `revealFor` in `steps.ts` decides between the three (stay, nearest, centred) from the keys of the current step, of `shown` and of `pointed`; `byPointer` tells a click of the pointer from one made with a key. The component only keeps the two keys and moves the track.
- **A tooltip with the name where the page does not show it in full** (`tooltipOf`): always on a step without a label, and on one whose label is cut. A step which cannot be chosen has it too: in a read-only, disabled or compared field without labels nothing else says what the steps are. The app's directive is made for disabled elements and only waits less long for them (`app/src/directives/tooltip.ts:10-16, 72`); a disabled button takes no focus, so there the tooltip is for the mouse alone.
- **Labels are measured only when something changed.** `measure` compares the scroll height of each label with its two lines: when the track is laid out or resized, when the steps or the current step change, and once the fonts have loaded. "The steps change" means what `signatureOf` makes of them, their keys and labels, not the list itself: the form hands every interface its options as a new object with every change of any field, a key typed into the input beside the track included (counted in the sandbox: ten keys, ten new lists, in a form with and without conditions). A watch on the list would read the layout of every label of every track on each keystroke.
- **The tooltip is also for the keyboard.** The app's directive listens for the mouse only (`app/src/directives/tooltip.ts:20-27`). On `focusin` a button which matches `:focus-visible` is sent a `mouseenter` of our own, and on `focusout` a `mouseleave`; the directive's listeners are on the button and neither event bubbles, so nothing else hears them. The `mouseenter` is sent a tick after the focus arrived: the focus moves the tab stop, which draws the track again, and the directive drops a tooltip which is still waiting whenever its element is drawn again (`app/src/directives/tooltip.ts:29-50`). A choice with Enter draws the component again too; the tooltip comes back with the next focus.
- **One tab stop.** The buttons have a roving `tabindex`: 0 on one of them and -1 on the others (`tabStop`). At rest that one is the current step, or the first where no step is current, so Tab enters the track there. While the focus is on a step it is that step (`focused` holds its key, set on `focusin` and cleared when a `focusout` leaves the list), so the next Tab leaves the track instead of landing on another step of it. The arrows, Home and End move the focus with `focus()`, which a `tabindex` of -1 allows. `focused` is also cleared when the track becomes inert, since a button which becomes disabled loses the focus without every browser saying so.
- **The list is named after its field** (`trackName` over `fieldData.name`, which the form passes to every interface: `app/src/components/v-form/components/form-field-interface.vue:77`). The form prints that name above the track but does not tie it to the interface, and a list called "Steps" in every field cannot be told from the next. "Steps" is only the fall-back. The `ol` also says `role="list"`: Safari with VoiceOver takes a list styled `list-style: none` for no list, and then does not say where a step stands.
- **Inert and dimmed are two things.** `disabled`, `nonEditable` and `loading` each make every button natively `disabled`, so none is a tab stop and nothing is emitted. Only `disabled` without `nonEditable` dims the box. That is how the stock Radio Buttons treat the comparison views (`app/src/components/v-radio.vue:96-112, 144-162`).
- **The focus ring is the app's.** The global rule of `app/src/styles/_base.scss:45-49` draws it on any button with keyboard focus. The buttons only turn it inwards (`--focus-ring-offset`), so it lies within the button, and the scrolling track cannot cut it off.
- **Forced colours are CSS only:** a `@media (forced-colors: active)` block at the end of each component's styles. Under a contrast theme of the system the browser takes every colour which is not a system colour away, backgrounds included, and in 1.0 that left a done marker the ring an upcoming one is, no lines, no thumb in the scrollbar and no pips at all.
  - In the track a done marker is filled (`Highlight`, its number or icon in `HighlightText`), the current one has a ring twice as wide in `Highlight`, an upcoming one a plain ring in `CanvasText`: three states which differ without colour, also in the compact form, where no bold label marks the current step. The wider ring is inside the marker (`border-box`). The lines are `Highlight` after a done step and `CanvasText` otherwise, the thumb of the scrollbar `CanvasText`.
  - **The marker opts out of the mode** (`forced-color-adjust: none`). Chromium paints a plate in the colour of the page behind text under forced colours, which hides a number in `HighlightText` on its fill. Having opted out, the marker gets nothing from the browser, so every colour of it is set in the block, and `!important`, because the rules for hover and for a dimmed field are more specific and would paint it in the colours of the theme. For the same reason the focus ring round a compact marker is set to `Highlight` there, which is what the app's own ring computes to in that mode in Chromium.
  - A step which cannot be chosen has its number and ring in `GrayText`, the colour the browser gives the label of a disabled button, and a dimmed field draws nothing at half strength: the mode is for contrast.
  - In the display a pip which is not filled is a ring of one pixel in `CanvasText` and a filled one a dot in `Highlight`, both still 6px.
- **Colours change softly only after a step was chosen by hand** (`animated`): the first change of state is the item arriving in the form, which would fade every track of the page.
- **Nothing drawn for an icon leaves the marker.** An icon name is not checked against a list, which changes with the app. A name the app does not know is drawn by `v-icon` as text, many times wider than an icon, so the icon is cut to its own box and the marker to its circle (`overflow: hidden` on both). What is left of an unknown name is its first letter.
- **The display is inline text with one atomic piece.** Its root is an inline `span`, as the stock text display is, so in a display template the label is part of the line and the template's own ellipsis cuts it. A table cell is a flex container, which makes the root a block; only then do its own `overflow`, `white-space` and `text-overflow` apply and cut the label at the edge of the cell. The pips are an `inline-flex` with `role="img"` and a name ("Step 2 of 4", from `positionText`), and never shrink. The count has the same role and name, or it would be read as "5 slash 12". A pip which is not filled is in `--theme--foreground-subdued`; the accent colour of the borders, which it had in 1.0, is 1.4 to 1 against the page and could be overlooked, and "2 of 4" then reads as "2". The count and the label are each isolated for the order of the line (`unicode-bidi: isolate`): in a right-to-left page "5/12" and a label in Latin letters would otherwise form one left-to-right run, with the count on the far side of the label. The app does not call a display for `null` and draws its own dash (`app/src/views/private/components/render-display.vue:25`); an empty text does arrive, and gets the same dash.
- **The display reads the interface's options.** The app passes them as `interfaceOptions` (`app/src/views/private/components/render-display.vue:28-37`), and the handler gets them in its context, so `progressOf` runs `readSteps` over the same `choices` and the two entries cannot disagree.

## Invariants: do not break

1. **Stored values and option keys are public API.** The field holds the `value` of a step, text or a whole number, and the interface never writes anything else, `null` included. The ids `steps` (interface) and `steps` (display), the option keys `choices` and `showLabels`, and the keys `text`, `value` and `icon` of an entry of `choices`, keep their names and meanings, and a missing `showLabels` means on. `choices` and the keys of its entries are also those of the stock Dropdown (`app/src/interfaces/select-dropdown/index.ts:14, 41`); keep them in step, so a field moves between the two by changing its interface alone. Other keys of an entry, such as the Dropdown's `color`, are left alone and ignored.
2. **Match loosely, write strictly.** A field configured elsewhere may hold numbers while its options hold their text, or the other way around. Both must keep showing their step, and what is written must stay in the type of the field. The unit tests and the browser test of the integer fields pin this.
3. **Never emit while inert.** The form drops what a disabled field reports in most cases, but not when the field is disabled because another user holds it in collaborative editing. `choose()` returns before it emits, and the buttons are natively disabled as well.
4. **Nothing falls through.** `inheritAttrs: false` in both components, and no template binds `$attrs`: the form passes some twenty props and two listeners to every interface, and a layout a handful to every display.
5. **The options are untrusted.** Text reaches the page only through `v-text`, the stored value in the warning included. Nothing from the options reaches CSS. An icon name goes to `v-icon` as it is, and whatever that draws stays inside the marker: keep the two `overflow: hidden`.
6. **`steps.ts` stays free of Vue, the DOM library and Directus.** `tsconfig.test.json` type-checks it without the DOM library.
7. **Bundle hygiene.**
   - The root `AGENTS.md` has the rules. There are no dependencies to bundle, and none should be added. `vue-i18n` in particular is not imported: `src/i18n.ts` reads `$t` from the app.
   - `dist/app.js` is about 21 KB (21,188 bytes, 6.7 KB gzipped, in 1.1.0; 18,786 and 6.2 KB in 1.0.1) and `dist/api.js` 72 bytes. About half of it is the styles, which the SDK ships unminified. Report size changes.
   - **No comments in the `<style>` blocks.** The build keeps them in the bundle (they were 2.6 KB of it), so what the styles rely on is written at the end of each component's script, which is not shipped, and under "How it works" here. `tests/bundle.test.ts` fails on a comment in either style block or anywhere in `dist/app.js`, and on an import of the bundle which is neither `vue` nor the SDK.
8. **It is an app-only bundle,** so the Marketplace can install it under the default `MARKETPLACE_TRUST`. Don't add API entries casually.
9. **Directus look.** Only `--theme--*` tokens for colours, and the form-input tokens for the box, so it matches the inputs beside it in every theme.
   - **One exception: the focus ring round a compact marker** is drawn in `var(--focus-ring-color, var(--theme--primary))`, at the width `var(--focus-ring-width, 2px)`. Those are the app's variables, not the theme's: the app draws every focus ring with them (`app/src/styles/_base.scss:45-49`) and sets the colour to the theme's primary colour itself (`app/src/styles/_variables.scss:21, 26`). Read through the app's variable, the ring round a marker stays the ring of every other control of the form, also if a later release gives focus rings a token of their own. The theme's primary colour stands in where the app has no such variable.
   - The app variables which are not theme tokens are `--fast`, `--medium`, `--transition`, `--focus-ring-offset-invert`, `--focus-ring-width` and `--focus-ring-color`. Each is read with a fallback. `--focus-ring-offset` and `--v-icon-color` are set for the app's own rules, not read.
   - **The other exception: the colours of the system under forced colours.** The rules inside `@media (forced-colors: active)` name `Canvas`, `CanvasText`, `Highlight`, `HighlightText` and `GrayText`, because the browser takes a token of the theme away there. No system colour stands outside those two blocks, and no token of the theme in a colour property inside them.
   - `tests/bundle.test.ts` checks all of this: no colour written out, no word in a colour property but a theme token, system colours under forced colours and only there, and no other variable than these six, each with its fallback.
   - Styles are scoped; class names other than the two roots (`steps`, `steps-display`) and the notice (`steps-empty`) start with `st-` in the interface and `sd-` in the display.

## Code style

The root `AGENTS.md` has the style of the repository. In this package also:

- `src`, `tests` and `sandbox` are laid out as Prettier 3.3.3 lays them out with `--print-width 160 --use-tabs --tab-width 4 --single-quote`; `npx prettier@3.3.3 <those flags> --check src tests sandbox` passes. Prettier is not a dependency.
- The unit tests cover `steps.ts`, and `bundle.test.ts` the rules for the styles. Everything else in the two components has to be checked in a browser, so what can be decided without one is decided in `steps.ts`: the component keeps the state and asks.
- The names of a step's three fields in the settings are the app's own strings (`$t:text`, `$t:value`, `$t:icon`) and the placeholders are the Dropdown's, each of which says exactly what is meant. The name of the option, "Steps", "Show Labels" and the notes have no such string and are plain English. `text` is not required; `value` is. The row of the repeater is `{{ text }} ({{ value }})`, so a step without a text can still be told from the others there.
- The options are a function of the field, as the Dropdown's are, only to give the `value` input the type of the field. Keep it that way: an untyped input writes text into the options of an integer field.

## Demo

`demo/demo.mjs` describes the demo in the sandbox (see `sandbox/README.md`, "Demos"): the collection `demo_steps`, whose six items differ only in how far they have come (first step, a third and two thirds of the way, last step, a value which is not a step, none), a form with the tracks in five groups by topic, a table preset of the recipes with the display, and a bookmark "More cases" for the rest. A few fields hold the same value in every item (`FIXED`), because their value is the point. The items take their values from `drawn()`, the demo's own reading of the choices, which is looser than `readSteps` in two ways its comment names. The note of each field lists the values its steps store, with their icons, since the form shows only the labels (`brief`, up to eight steps). A new or changed option, or a rule for entries which are left out, gets a field in a group. `sandbox/demo.spec.ts` builds it and checks that every field draws a track or the notice of a field without steps, and every value in the table and in its bookmark the display.

## Testing in a browser

`sandbox/steps.spec.ts` creates the collection `sandbox_steps`, with a stock input and a stock Dropdown beside the tracks, the collection `sandbox_steps_rows` with a stock Repeater, and two users of its own (one with the dark theme, one who reads German), and checks in Chromium that the built bundle loads and:

- the track draws the state of the value: done, current and upcoming, as an ordered list with the role written out, named after its field and so unlike the list of every other field of the form, of buttons named by their labels, with one current step, icons from the choices of a Dropdown, and nothing of what the form passes on the box;
- entries without a value or with a repeated value are left out, and a step without a text has no label and is named by its value;
- a field which holds nothing has no current step and no warning; the label of an upcoming step is in the text colour of an input, as that of a done step, its marker is quiet and empty, and a done marker is filled;
- a click on a label and on a marker chooses a step, forwards and backwards, the saved item holds its value, and a click on the current step leaves the form unchanged;
- the field is one tab stop: Tab enters the track at the current step and the next Tab leaves it, also from a step the arrows went to, in either direction; a field without a value is entered at its first step; Enter and Space choose, the chosen step is where the track is entered afterwards, and the arrows, Home and End move the focus, stop at the ends and change nothing;
- an integer field, with numbers and with their text in its options, shows its step on load, sends and stores a number, and shows the chosen step after a reload;
- the options form gives the value of a step a number input on an integer field, says in the note of the list that a value which is not a whole number is left out, and stores a number, and nothing in the step but what was typed;
- a field with four texts and `showLabels` off draws no label, names its steps by their texts, shows a text as a tooltip, is exactly as high and as wide as the stock input in the same row and starts on the same line, with markers of the usual size on its middle line; twelve such steps beside a stock Toggle scroll in columns narrower than 4.5rem at the same height; a field with labels switched on and no text is compact too; a click chooses and the item saves it;
- a field with two steps with a text and two without draws two labels, one of them for a step which still holds the old `showLabel: false`, names all four for assistive technology, is not compact, shows the name of an unlabelled step as a tooltip for the mouse and for the keyboard, and shows none for a labelled one; a field without the option shows its labels;
- a read-only field is dimmed, has every label in the subdued colour (an editable one has not), is passed by the Tab key and does not change;
- a read-only field without labels shows the name of a step as a tooltip for the mouse, and one with labels has none;
- a condition which makes the field read-only makes the track inert and dimmed and takes its tab stop away, before anything is saved, and the track is back when the condition no longer matches;
- in the comparison of two revisions both tracks of a field show their step, every track is inert and none is dimmed, the one of a read-only field included, a compact one shows a tooltip, a click changes nothing, and nothing is sent;
- nothing in the track fades before a step was chosen by hand, the marker, the label and the line fade afterwards, and with `prefers-reduced-motion` nothing takes any time;
- under forced colours a done marker is filled and its number is not in the colour of the fill, the current one has a ring twice as wide as an upcoming one, every marker keeps its size, the lines and the thumb of the scrollbar show, the mouse on a step changes nothing, a read-only field has nothing at half strength and its markers in the colour of its labels, the focus ring round a compact marker is in a system colour, and in the table a filled pip is a dot and one which is not a ring, both 6px;
- a value which is not a step is named in a line inside the box, between quotation marks, the list is described by that line, and the line goes when a step is chosen; a value with spaces at its ends shows them;
- keys typed into another field make no track ask a label for its `scrollHeight`, and a step which is chosen does;
- a field without steps shows the stock notice and no box;
- twelve steps in half the form scroll inside the box with the last, current step in view, equal columns of at least 4.5rem, a styled scrollbar with a thumb in the subdued text colour, and nothing else on the page moved sideways; four steps fit the same width;
- on that track a double click on a step which is wholly in view makes that step the current one and leaves the track where it is, with the same step under the pointer; a double click on the visible part of a step which is cut by the edge moves the track by what was hidden and no more; a save does not move it; a step chosen with Enter goes to the middle;

Things which are easy to trip over:

- **Playwright's headless Chromium hides every scrollbar,** so a picture of the track shows none and the track is no taller for it. The spec checks the style of the scrollbar instead. To see it, start Chromium with `ignoreDefaultArgs: ['--hide-scrollbars']`.
- **The app's tooltip is one shared element with one timer,** and every component which uses the directive drops a waiting tooltip when it is drawn again (`app/src/directives/tooltip.ts:29-50`). A mouse which arrives while the page is still settling or scrolling therefore gets none. The spec's `expectTooltip` moves the mouse away and back until the tooltip shows.
- **That a step has no tooltip is not shown by waiting for none.** The directive marks an element with `data-tooltip` when it is given a text and not before (`app/src/directives/tooltip.ts:20-27`), so a step which never had a tooltip has no such attribute (`expectNoTooltip`). The attribute stays once it was set, so this says nothing about a step whose tooltip went away.
- **A disabled button still gets `mouseenter`** in Chromium, which is what the tooltip of a read-only field relies on. Playwright's `hover()` does not ask whether its target is enabled; `click()` does, so the tests which show that a click changes nothing click with `force`.
- **The tests which need another user make one** (`makeUser`: the dark theme, German) and sign in with a browser context of their own (`signedIn`), so no test changes the administrator, whom every other spec signs in as. The users are told by the start of their address, `sandbox-steps-`, and removed before and after the run.
- **Forced colours are emulated per page** (`page.emulateMedia`), and Chromium's emulation has colours of its own: a dark blue `Highlight` at four fifths strength on a light system, which is close to the black of `CanvasText`. So the test compares what is painted with the ground it stands on and one state with another, never with a colour written out. The plate which Chromium paints behind text in this mode is paint only and shows in no computed style; the test therefore asks whether the marker opted out (`forced-color-adjust`), and the numbers were looked at in pictures.
- **A picture of one element can show the page half without the emulation.** `locator.screenshot()` of a row of the table came out with its text and its filled pips in colours which were not the forced ones, while `page.screenshot()` a moment before showed the row as the computed styles say. Take the page and cut it.
- **Counting what a track measures:** the test of the keystrokes replaces the getter of `Element.prototype.scrollHeight` in the page with one which counts the questions asked of a `.st-label`. The count is taken once two readings agree which are an interval of `expect.poll` apart (a tenth of a second or more), because a page which was just opened may still be laying itself out. The first reading is compared with -1, which no count is: the poll asks its first question at once, and two readings a few milliseconds apart would agree on a page which is still moving.
- **The tests share one item and change it.** Each test which changes a field first puts that field back through the API (`reset`), so it does not depend on what an earlier test, or an earlier repeat of itself, saved. A second item (`still`) is never changed.
- **Right-to-left needs no user, but not the root element either.** The app writes `dir` on the root element again with every update of the document head. The spec's `turn()` sets it on `body`, and the tests which use it check at the end that the direction is still the one they set. A track which was already scrolled is not moved when the direction changes under it; a user whose language is right-to-left never sees that, since the direction is there before the track.
- **A line between two steps is a pseudo-element,** which has no box to ask for. The spec works its place out from the computed `left`, `top`, `width` and `height` of `::after` (`geometry`).
- **Text which overflows cannot be found with `elementFromPoint`.** The test of an unknown icon name compares pictures of the field with the marker painted over, with the icon shown and with it hidden. A page which was just opened is still moving, so a picture only counts once the next one equals it.
- **The form hands over `null` before the item arrives,** so a test first waits for the states it expects.
- **`page.mouse` does not wait as a locator does.** For a moment after a page has loaded, the app's cover (`.hydrating`), which is fading out, still takes a click. The pointer test needs raw coordinates, to click the visible part of a step which is cut by the edge, and first waits until the step is what `elementFromPoint` finds there.
- **A locator's click scrolls its target into view first,** inside the track too, so it cannot click a step which is partly hidden as a user would. That is the other reason for `page.mouse` there.
- **Two tracks of the fixture scroll** (`year` and `crowd`), so "nothing else on the page was moved sideways" counts the elements which are not a track (`strays`).
- **The API turns the text of a number into a number,** so the saved item cannot show whether the interface reported `4` or `"4"` for an integer field. `save()` returns the body of the request the form sent, and the tests compare that. Nor can a browser test see that a click on the current step reports nothing, since the form takes an unchanged value for no change: the unit test of `chosen` covers it.
- **A collection which points at `sandbox_steps`** (a many-to-one made by hand to try a template) stops the spec from dropping it. Delete that collection first.

## Known gaps

- Only Directus 11.17.4 has been tested, and only in Chromium: not Firefox, Safari or a touch device. The scrollbar of the track in Firefox, which has no `::-webkit-scrollbar`, was not looked at.
- Not tested with a screen reader. The roles, names, descriptions and the current step were checked through the accessibility tree which Playwright reads. In particular it was not heard whether a screen reader reads the description of the list, which is the warning, when the focus enters the track, nor whether VoiceOver in Safari says the position of a step now that the list has its role written out.
- The tooltip of a step which cannot be chosen relies on a disabled button getting `mouseenter`, which was seen in Chromium only. A browser which sends a disabled button no mouse events shows no tooltip there, as 1.0 did everywhere.
- A pip of the display which is not filled is in `--theme--foreground-subdued`: 2.1 to 1 against the page in the default light theme and 3.3 to 1 in the dark one. No token reaches 3 to 1 in both and stays apart from the primary colour. In the dark theme its luminance is that of the primary colour (1.03 to 1), so a filled and an empty pip differ by hue alone there; the name beside the pips and their accessible name say the same without colour. Pips which are rings while empty would not need colour; that is a change of the look and was not made.
- Collaborative editing, where a field is disabled while another user holds it, was not tried: the sandbox runs without websockets.
- `loading` was not seen on its own: the form sets `disabled` whenever it sets `loading`.
- `nonEditable` was seen in the comparison of two revisions only. A content version compared with the main item, and a user who may not update the field, were not tried.
- Forced colours were seen as Chromium emulates them only, with a light and with a dark system: no contrast theme of Windows, and no Firefox or Safari. Chromium's emulated `Highlight` is partly see-through, so a done marker shows a slightly darker edge where its border lies over its fill; an opaque system colour does not.
- Under forced colours a step shows no change when the mouse is on it, apart from the pointer.
- Not tried with a custom theme which sets the form-input tokens apart from the page's, nor with one whose input is lower than a marker and its ring: the compact box then grows to fit the marker, by the `max()` in its rules, which was not seen.
- The compact form's scrollbar in a browser without `::-webkit-scrollbar` (Firefox) is as thin as `scrollbar-width: thin` makes it, which may reach the focus ring of a marker.
- The number or icon in the marker of an upcoming step, and the thumb of the scrollbar, are in `--theme--foreground-subdued`, about 2.1 to 1 against the box in the default light theme. Neither is the only carrier of anything: the label names the step, and the cut marker at the edge shows that the track goes on.
- The warning for a value which is not a step, "Completed" for a step which is passed, "Step 2 of 4" of the display's pips and count, and the name "Steps" of the list of a field without a name are English only.
- The warning's icon is read as the word "warning" before the sentence, since the app draws an icon from its name. The description of the list is the sentence alone.
- An icon name which the app does not know shows as its first letter. Nothing says that the name is wrong.
