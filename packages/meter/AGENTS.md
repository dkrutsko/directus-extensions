# directus-extension-meter

A Directus 11 bundle extension, published on npm as `directus-extension-meter`. It adds the **Meter** interface (`meter`) and the **Meter** display (`meter`) for `integer`, `bigInteger`, `float` and `decimal` fields which hold a number that something else keeps up to date. The interface draws the number as a bar which is filled as far as the value has come between a minimum and a maximum, with the value as text beside it and a caption under it; the display draws a short bar of a fixed length and the text in layouts. In both the track can instead be a row of pills, segments, bars or dots, each filled or not, as many as the width allows, the colours of the thresholds can belong to places on the scale instead of to the current value, and the piece which comes next can grow or fade in as the value nears it. In a field which can be edited the interface is also the control: the pointer and the keys set the value. In a read-only field it is a reading and nothing else, which is what it was made for: the stock Slider is a control which greys out there, and the stock displays show a number without its range.

The rules which hold for every extension of this repository (independence, bundle hygiene, code style, releasing, the sandbox) are in the root `AGENTS.md`. This file only holds what is specific to this package; `CLAUDE.md` imports it.

## Commands

Run these in this folder, after `npm install` in the repository root:

```bash
npm run dev        # watch build, unminified
npm run check      # vue-tsc, plus tsc over the tests (tsconfig.test.json)
npm test           # vitest
npm run build      # dist/app.js + dist/api.js
npm run validate   # directus-extension validate
```

`prepublishOnly` runs check, test, build and validate.

## How it works

- **A bundle with an app side only.** The manifest has the two entries and no hook, endpoint or operation. The SDK still writes `dist/api.js`, three empty lists, because a bundle has both paths. The entry names differ (`meter`, `meter-inline`), as a bundle needs; the ids are the same, since Directus registers interfaces and displays apart. The stock id `meter` is a panel of Insights, a third registry.
- **The display never writes. The interface writes only where its field can be edited.** `editable` in `interface.vue` is `canEdit(props, method)`, which is `!disabled && !nonEditable && !loading`, the three props by which the form says that a field is read-only (by its settings, by a condition, by the permissions of the user, in a batch edit), shown where nothing is edited (the comparison of revisions) or still loading, and `method !== 'none'`.
  - **The input method `none` is settled in two lines and nowhere else:** `inputMethod` returns `none` before it looks at anything, and `canEdit` is false for it. So a meter set to `none` is not editable, and everything below which is written for a field that cannot be edited holds for it without a check of its own: no handler, no template condition and no style knows the word. Its field is still one the form lets it edit, which is why the test of it asks for the listeners and compares it, element for element and box for box, with the same meter in a read-only field.
  - **Not editable is the meter of 1.0.1,** element for element: the role `meter`, the classes and attributes it had, no `tabindex`, no handle, no listener (the template binds `v-on` to an empty object), no cursor, no `touch-action`. It is not dimmed: a field which a flow maintains is normally read-only, and dimming it would dim nearly every meter.
  - **Three things stand between a field which cannot be edited and an emit,** on purpose: no listener is bound; every handler returns at once unless `editable`; and `write`, through which every value goes, checks it again. `finish`, which puts a value back on Escape, checks it too. Take none of them out because another is there.
  - **The form is a fourth, and hides mistakes.** The item form of 11.17.4 drops what a disabled field hands it (seen: with every guard of the meter taken out, a click on a read-only meter still changed nothing in the page). So a test which only looks at the value proves nothing about the meter. The browser tests ask the browser which events the element listens to (`DOMDebugger.getEventListeners` through a CDP session, `listened()` in the spec): none for a meter which cannot be edited, six for one which can.
  - **`nonEditable` and `loading` were not seen on their own.** In the comparison of revisions the app sets `nonEditable` together with `disabled`, and while a form loads it covers the field. The rule for all three is a pure function with unit tests of every combination.
  - **A field which stops being editable during a drag** lets go of the pointer and of the lock at once (`watch(editable)`). A condition on the field's own value does that: the field `closing` of the spec is read-only from 50, and a drag across 50 closes it with the button held.
  - **This changed what existing fields do.** Before, no meter wrote. A field whose meter must stay a reading has to be read-only in its settings; the README and the changelog say so.
- **What is written is made in one place** (`snapValue`), and `write` takes nothing else: a finite number, on the grid of steps counted from the minimum, within the range, or the maximum.
  - **The grid starts at `min`.** `min + n * step`, for a whole `n`. A range from 1 with steps of 2 has 1, 3, 5.
  - **The maximum can always be written,** also where the grid misses it: steps of 3 from 0 to 10 are 0, 3, 6, 9 and 10. Otherwise a meter could never be full. Between the last point of the grid and the maximum the nearer of the two wins.
  - **No dust.** The result is rounded to as many decimals as the step, the minimum and the maximum have between them (`decimalsOf`, from how the numbers are written out), so `0.1 * 3` is written `0.3`. With more than 15 decimals nothing is rounded.
  - **Whole types.** `integer` and `bigInteger` (`type`, which the form hands every interface) get a whole step of at least 1 (`readEditing`), a grid which starts at the first whole number of the range, and a whole number. A range without a whole number in it has nothing to write (`null`), and nothing is written.
  - **One range for everything which edits** (`writableRange`): the range as it is drawn, and for a whole type `ceil(min)` to `floor(max)`. The grid of `snapValue` starts at its minimum. `automatic` is `piece` only where it is the drawn range itself. A key counts from its nearer end for a value from outside, Home and End are its ends, and a piece of a Page key is a piece of it. A slider says it as `aria-valuemin` and `aria-valuemax`. The drawing does not use it: the fill is still against `min` and `max` as stored, and a meter which cannot be edited says those. Before there was this one range, an integer field from 0.5 to 5.5 in five pills filled by the piece wrote n + 1 for a press on piece n.
  - **Everything which moves along the grid counts its points** (`gridOf`, internal). The points of a range are numbered from 0 at the minimum, with the maximum as the point after the last one where the grid misses it (`top`); `at(index)` turns a number into the value, cleaned as above, and `around(value)` gives the numbers of the points below and above a value, twice the same for a value which is on a point. Two numbers are one point when they are a hair apart against a step (1e-9 of it, or of the range where the step is larger) or as close as numbers of their size can be (four of their spacings). `snapValue` and `keyValue` both go through it. Never add a step to a value and look where it landed: `(value + step - min) / step` is off by more than any fixed slack once a grid holds some tens of millions of steps, and a key which worked that way did nothing at nearly half of the values of 0 to 10,000,000 in tenths (found by the reviewer).
  - **Steps which make no grid.** A step larger than the range leaves the two ends of the range, points 0 and 1, and the nearer is written (a key takes the end it points to). A grid holds as long as its points can be counted exactly: up to `MAX_STEPS`, which is `Number.MAX_SAFE_INTEGER`. Only a range which holds more steps than that, or whose limits are too far apart to subtract, has none: the value within the range is written, rounded to `FREE_DIGITS`, twelve, digits which count. So 0 to 2,000,000,000 with a step of 1 writes whole numbers. An earlier cut-off at a thousand million steps wrote fractions there.
  - **A number for every type.** The stock Slider of 11.17.4 sends a JSON number for `integer`, `bigInteger`, `float` and `decimal` alike (seen in the body of the request which saves an item: `6`, `6`, `4.5`, `4.5`). The stock Input sends a number too, but for `bigInteger` the text `"7"`. The meter does as the Slider does. A big integer beyond 2^53 is therefore not exact, as in the Slider.
  - **Three roundings.** The pointer goes to the nearest point, with the upper one half way. `'down'` and `'up'` are the points below and above, which `pieceValue` asks for around its target.
  - **Only a change is written:** `write` asks `changes(held, next)`, which compares with the number the field holds (`numberOf`, so the text `"5"` of a decimal is 5). The form would drop an edit which equals what is stored, so this too is pinned by unit tests and not seen in the page. The one thing which is emitted without going through `snapValue` is what Escape puts back: exactly what the field held at the press, be it `null` or a value from outside the range.
  - **The step is `step`,** and `stepInterval`, the key of the stock Slider, while `step` is not set (missing, `null` or blank), as `minValue` and `maxValue` stand in for the limits. A `step` which is set and is no number above zero is 1; it does not fall through to the Slider's.
  - **With neither, the step suits the range** (`defaultStep(range, whole)`, the last fall-back of `readEditing`, which is handed the range the meter is drawn against): 1 for a whole type, as before; for any other type the largest power of ten which still gives the range at least `STEPS_WANTED`, a hundred, steps, and never more than 1. A range of 1 or of 5 has 0.01, one of 10 or of 50 has 0.1, one of 100 or more has 1. Before it, a float field from 0 to 1 could be set to 0 and to 1.
  - **The power is made from its text** (``Number(`1e${exponent}`)``), so it is the double of that decimal and no other: `0.1 ** 2` is 0.010000000000000002. `decimalsOf` then reads its decimals off it and `gridOf` cleans every point to them, which is what writes 0.37. The logarithm only proposes the exponent; two loops move it to the largest power which fits, with a hair of slack (1e-9 of a hundred) for limits such as 0.6 and 0.7, whose difference is a hair under a tenth.
  - **It holds down to fifteen decimals** (`LEAST_STEP`, 1e-15), which is as far as a written value is cleaned (`gridOf`: more decimals than fifteen are not rounded). A range of 1e-13 still has its hundred clean steps; a smaller one gets steps of 1e-15 and fewer of them, and one below 1e-15 is left with its two ends, like any range smaller than its step. A range of one number, and limits which are not finite or too far apart to subtract, have 1. A unit test writes every point of eleven ranges through `snapValue` and compares it with its decimal text.
  - **The consequence for `automatic`:** on a float or decimal field without a step a piece is no longer one step, so five pieces for 0 to 5 are set by position, in hundredths, where they were set by the piece. A step of 1, or `piece` as the method, brings whole pieces back; the README says so.
- **The input methods, and why `automatic` chooses as it does** (`inputMethod`). The words are `position`, `piece`, `relative` and `none`, with `automatic` for the first two; the form calls them "By position", "By piece", "Relative" and "None". No input method is called by a word of the visualizations any more: `contiguous` and `segment` were the names of the first two in builds which were never published, are not read, and a field which stored one reads as `automatic`, like any other junk. (`contiguous` and `segments` are still two of the five visualizations.)
  - **`position`:** the share of the track at the pointer, as a value, snapped. For packed dots the track is the row of dots (`frame().length`), not the width of the field, or a click on the fifth of ten dots would give a quarter.
  - **`piece`:** `filledAt` counts the pieces whose start the pointer has reached, in `pieceGeometry`, the same data the pieces are counted and laid out by; what is written is `pieceValue`: of the values which can be written and which draw exactly that many pieces, the one nearest to that share of the range, so that the piece which was pressed is the last one filled; where no value draws that many, as with more pieces than steps, the nearest value. Where a piece is a step that is the share itself. A gap belongs to the piece before it, before the first piece is the minimum, beyond the last is the maximum. On one bar there are no pieces, and it is `position`.
  - **`relative`:** `relativeMove` adds `movement / length * range * sensitivity` (a tenth of it with Shift) to a value which is kept unsnapped for the length of the drag (`drag.raw`), within the range, and what is written is that value snapped. Kept unsnapped, forty movements of a quarter step are ten steps; kept within the range, the first movement back from an end counts.
  - **`automatic` is `piece` exactly where `count * step` is the range and the limits themselves can be written,** which is where a piece stands for one step and a click on the third piece can only mean three steps. Where a piece is several steps, as ten pieces for 0 to 100 at a step of 1, filling by the piece could reach only every tenth value of the grid, so the pointer sets the value under it instead and all hundred can be reached. Where a piece is less than a step the pieces mean nothing as targets either. It is never `relative`: that method changes nothing on a press, which nobody expects of a meter they did not set up that way.
- **The target is taller than the track, and never leaves the area.** Two more items of the root's column, only on a meter which can be edited (`mt-reach`): `mt-above`, which is after the track in the markup and drawn before it by `order: -1`, so that the track stays the first child, and `mt-below`, the last. Each is `flex: 1 1 0` with a `max-block-size` of 0.5rem, and the gap of the column beside it is taken back by a negative margin. So each takes the room the area has free on its side, up to 8px, and none where there is none; growing alike they leave the group in the middle, exactly where `justify-content: center` puts it without them, which the twins of the spec compare. Being items of the root, neither can reach outside it: under a caption of several lines the track is at the top edge of the area and `mt-above` has no height. An earlier version hung a box of 8px above the track wherever the track was, which lay over the gap under the field's label and the last rows of the label itself (found by the reviewer). The 0.25rem between the track and the line of caption and text belong to the target as well, by a pseudo-element of `mt-above` laid under the track (`.mt-lined .mt-above::after`; the root has `mt-lined` when there is such a line). With the line, `mt-below` lies under the caption and takes no press (`pointer-events: none`); without it, it is right under the track and takes them. In a stock area that is 8px, the track and 4px, 24px in all. They are boxes beside the track and not one over it, so the track keeps its own events and the handle, the marks and the hover stay the track's. Their `pointerdown` (`pressBeside`) prevents the default, gives the track the focus and runs the track's own `onPointerDown`, which works from the track's geometry: a press there is a press on the track at the same place along it, by every method, and Escape and the keys work after it. For a finger or a coarse pointer the root listens too (`onAreaDown`) and takes a press anywhere above the top of the line of caption and text.
- **Pointer events, one press at a time.** `pointerdown` of the primary button of the primary pointer starts a drag and captures the pointer, so the drag goes on outside the field; `pointerup` ends it, `pointercancel` ends it and puts the value back. `touch-action: pan-y pinch-zoom`, on the track and on the whole area of a meter which can be edited, leaves vertical scrolling and a pinch to the page. `lostpointercapture` is not listened to: a pointer lock takes the capture away when it is granted. A press which never saw its release is ended by the next press, and by a mouse which moves with no button held.
  - **A finger writes nothing by coming down** (`drag.pending`). The first write is that of a sideways drag, once the finger has moved `TOUCH_SLOP`, 6px, along the track and further along it than across (`sideways`), or of the finger being lifted, which is a tap and writes what a press there writes. A `pointercancel` before either, which is what the browser sends when it takes the finger for a scroll, has nothing to put back and emits nothing. Before this a touch wrote at once and the cancel put the value back, which could not be done on a field which the written value had closed by a condition: a scroll which started on such a meter left an edit behind (found by the reviewer). That is closed for a scroll which goes straight up or down. One which starts with a few pixels of sideways drift is still a drag to the meter before it is a scroll to the browser, and writes: see the known gaps. The relative method writes nothing on a press anyway; for a finger its first write also waits for the sideways move, and then counts the whole distance from where the finger came down. A mouse and a pen write at the press as before.
- **Pointer lock, and its fall-back.** The relative method asks for the lock on the press (`requestPointerLock`, not for a finger). While `document.pointerLockElement` is the track, a movement is `movementX`; otherwise it is the difference of `clientX`, with the pointer captured. That question is asked at every movement, not remembered: the first movement under a lock arrives before `pointerlockchange` does (seen: a fifth of a drag was lost that way). The lock is given back on release. A lock which ends while the button is held was ended by the browser, as on Escape, and counts as Escape; one which arrives after the release is given back at once. A refusal (the promise rejects, or the method throws, or is missing) changes nothing: the drag is already working.
  - **In the sandbox's browser** (Playwright's headless shell of Chromium) the lock is refused: `WrongDocumentError`. The same Chromium started as the full browser (`channel: 'chromium'`), still without a window, grants it. The browser test of the relative method runs its steps in both.
- **Keys** (`keyValue`): Right and Up one step up, Left and Down one down, Left and Right swapped where the computed direction of the track is `rtl`; Page Up and Page Down ten steps (`PAGE_STEPS`), or the whole steps of one piece where those are more; Home and End the two ends of what can be written. A key counts in points of the grid: from the number of the point the value is on, one, ten or a piece further, and that number is turned back into a value, so no key lands on the point it started from and a Page key is always its ten steps (on every grid a field is likely to have; the known gaps say where numbers run out). A value between two points counts from the point behind it, so one step takes it to the next point and not past it (3.7 on a grid of 1: Right is 4, Left is 3). Where the numbers themselves lie further apart than the points, as at 1e15 with steps of a thousandth, the key goes on, twice as far each time, to the first point which is another number. Where there is no grid it adds the step and writes the value within the range. A value from outside the range is first brought to the nearer of those ends, and the key counts from there: 150 of a hundred and Left is 99, and 15 on a whole type from 0 to 10.5 is 9. A key of the meter's is `preventDefault`ed whether or not it changes anything, so the page does not scroll; a key with Ctrl, Alt or Meta is left alone. Escape is the meter's only during a drag, and is then stopped from going further.
- **What shows that it can be edited takes no room.** The cursor (`pointer`, `ew-resize` for the relative method). A handle on the one bar: a dot of 0.5rem inside the track at the end of the fill, clamped so that it is inside at both ends of the range, visible under the pointer, under the keyboard's focus and during a drag, shown and hidden without a transition. The pieces up to the pointer drawn larger than regular, on a meter whose pieces are filled by it (`hover`, `largeScale`): an inline transform on each of them, like the one of pieces which grow, in place of whatever size the piece had, so a small piece which grows and a filled one are equally large up to the pointer. Bars and segments are half as high again and no wider (`LARGE_ACROSS`); dots are a pixel more on every side, and pills a pixel more at each end and a third higher (`LARGE_ALONG`, in pixels, since two large pieces side by side must leave two pixels of their gap: the component reads the length of a piece at the moment and `largeScale` turns the pixels into a factor). A large pill is given the corner radii which the transform turns back into half circles (`roundEnds`). No piece gets a class, another colour or another box, the track and the target are what they were, and the pieces after the pointer keep what `grow` and `fade` give them. The row clips what is outside its box, so while pieces are large, and for a quarter of a second after the last one stopped being so, it has the class `mt-swell`: `overflow: visible`, and a transition of the transform and the radius over 150ms inside `prefers-reduced-motion: no-preference`. With no pointer on a meter the row and its pieces have the elements, classes and styles they had before there was any of this. It does not depend on `grow` or `fade`, and the display has none of it. This is the fourth look of these marks: a ring in the primary colour, a grey dashed line and a tint of the text's colour at 16% were tried before it, and the owner asked for the size (follow-up 11). What must not come back is what the first tint did wrong: it vanished at the press and stayed behind after the release. The marks are where the pointer is at every moment (`rest`): while it rests on the track, from the press on through a drag by its place along the track wherever it is, and at the release worked out again from where it is then, without waiting for it to move, so nothing above the pointer stays marked. A finger leaves none. A large piece reaches a few pixels outside the track, and a press there is a press on the track as it is beside the track anyway; in the 150ms in which a piece eases back it can still take a press just outside the track where the area has no room of its own, as under a caption of several lines. A focus ring as an outline. The app has its own ring for every focused `div`, drawn inside the element with square corners (`div:not([contenteditable=true]):focus-visible` in its global styles, which also sets `border-radius: 0`); the meter's two rules are written with one class more than they need to come before it, and give the track its round ends back.
- **Everything goes through `readOptions` and `readingOf`.** The components hold no arithmetic. `readOptions(own, inherited)` takes the options as the schema stores them, which is untrusted, and returns an `Options` in which every key has a usable value. `readingOf(value, options, locale)` returns what is drawn: whether there is a value, the fraction filled, the value kept within the range for `aria-valuenow`, the text and the colour. The interface calls `readOptions(props)`, the display `readOptions(props, interfaceOptions)`, the handler the same with the context it is handed, so the three cannot disagree.
- **The fall-back is key by key, and there are two kinds of key.** For the limits, the caption, `prefix` and `suffix`, `indicator` and the format, the first source which holds something usable wins: the entry's own options, then the options of the field's interface. Usable is a number or the text of one for a limit, non-blank text for the caption, the prefix and the suffix, a boolean for `indicator`, one of the three formats. So a cleared option (`null`), a broken one and a missing one all fall through, and `indicator: false` of the display wins over `true` of the interface. For `color` and `thresholds` only a missing key falls back: a key which is there counts whatever it holds, so an emptied colour is the default colour and an emptied list no thresholds. The reason is the options form. It shows the interface's colour and list as the default of its inputs only while the key is missing; once the user empties one, `null` is stored and the form shows an empty input, so the layouts must draw none. For limits and caption the form shows what is taken over as a placeholder, which shows whenever the input is empty, so there an emptied option can go on falling back. The display tells the two apart because an option which was never set arrives as `undefined` and an emptied one as `null`.
- **Four keys for two limits.** A limit is `min` or `max`, which are also the keys of the stock Input (`app/src/interfaces/input/index.ts:147, 156`), or else `minValue` or `maxValue`, the keys of the stock Slider (`app/src/interfaces/slider/index.ts:16, 25`). Both entries read both pairs from every source, `min` and `max` first. That is what makes the display work on a Slider field, and what keeps the range of a field which is moved from the Slider to the Meter: the app keeps a field's options when its interface changes, so such a field holds `minValue` and `maxValue` and no `min` or `max`. The interface therefore declares `minValue` and `maxValue` as props although its form has no input for them. Were only the display to read them, form and table of such a field would show two different ranges.
- **A field which holds both pairs is read by `min` and `max`, on a Slider field too.** One would expect the Slider's own pair to count there. It does not: the stock Slider of 11.17.4 does not declare `min` and `max`, so they fall through to the component inside it, whose range they are, and override the two it was given (`app/src/interfaces/slider/slider.vue:38-49`). A Slider field with `{ min: 0, max: 10, minValue: 1, maxValue: 5 }` runs from 0 to 10, with eleven ticks, and lets the user choose 10 (seen). The display has to show the range the form shows, so the order is the same for every interface. The browser test reads the limits from the Slider's own `input` and compares the display with them; should a later Directus make the Slider keep to its own pair, that test fails, and the order for a Slider field has to turn around (the display is handed the id of the field's interface as `interface`, the handler as `context.field.meta.interface`).
- **The range is put in order once.** `readOptions` returns `min` as the smaller and `max` as the larger of the two, after the fall-back and the defaults. Everything after it can rely on `min <= max`. With `min === max` the fraction is 0 below that number and 1 from it upward, and the percentage 0 and 100.
- **The bar is clipped, the text is not.** `fractionOf` stays within 0 and 1; `percentOf` does not, so 150 of 100 is "150%". A value strictly inside the range is never 0 or 100 percent: it is rounded and then held between 1 and 99.
- **Nothing which is not finite reaches the page.** `numberOf` takes a finite number, a big integer or the text of a number as the API writes it, and nothing else: not `Infinity`, not hexadecimal, not blank text. `shareOf` halves the numbers where their difference would overflow. A fraction is always finite, and so small a one that 1 over it is not, as 1e-300 of ten thousand million is, counts as nothing filled (`fractionOf`); the one number which is 1 over a fraction, the scale of a painted fill, goes through `fillScale` in both components, which is always finite. The text never holds `NaN`; a unit test runs extreme values against extreme limits for exactly that. The app's error boundary around a display does not contain an error thrown while the browser is handed a display's output: one bad cell can blank a layout.
- **Numbers are written by `Intl.NumberFormat` in the language of the user.** `useLanguage` reads `$i18n.locale` from the app's global properties, which is tracked, and falls back to `lang` of the root element (`app/src/lang/set-language.ts:28-30`); the handler has no component and reads the root element. A tag which the browser does not take falls back to the browser's language instead of throwing. Formatters are kept in a map, since a table makes one text per row. Value and maximum have at most two decimals; a number below 1 keeps two digits which count; from 1e15 upward and below 1e-6 an exponent is used, because the digits of a larger number are not all true and a smaller one would be a row of zeros.
- **The text of a number is marked as running from the left** (`dir="ltr"`) in both components. A number has no direction of its own: in a right-to-left page "-20%" would be laid out as "20%-" and "7 / 12" as "12 / 7". The number formatting of a right-to-left language puts the marks it needs into the text itself, so Arabic still reads from the right.
- **A prefix and a suffix are part of the value text, and of nothing else** (`prefix`, `suffix`; `valueText`). The value is prefix, number, suffix; the fraction has the prefix before each of its two numbers and the suffix once, at the end ("$4,200 / $10,000", "42 / 100 GB"); the percentage has neither, and neither has the dash of no value or a value which is no number, which never reach `valueText`. Since every text goes through that one function, the line under the bar, `aria-valuetext`, the display's tooltip and its `handler` have them without any code of their own.
  - **They are joined on as typed, as the stock Formatted Value display joins its own** (`app/src/displays/formatted-value/formatted-value.vue:137-140` and `app/src/displays/formatted-value/index.ts:15-16, 28`: `${prefix}${value}${suffix}`, with `trim: false` on both inputs, `index.ts:99-124`). So `readOptions` reads them like the caption, the first source with text which is not blank, but does not trim them: the space of " GB" is the user's, and the notes of the two options say that it has to be typed. The options form stores " GB" with its space (seen).
  - **`$t:` keys are translated by the app, not here:** its store of fields translates every string of `meta.options` and of `meta.display_options` when it loads them (`app/src/stores/fields.ts:169-171`), which is also how a caption picked from the translation strings arrives translated. A key is the whole string, so a translated suffix has its space in the translation or has none (seen: `$t:percent` as a suffix prints "4,200Percent").
  - **The display takes each from the interface while its own is not set,** like the caption, so it cannot have none where the interface has one. The options form shows what is taken over as the placeholder.
  - **They are inside the element of the number,** so the whole-or-absent rule holds for the text with them: a suffix of forty characters is on one line in half of the form, and in a field or a column without room for the whole text it is left out whole, with the track across the field, the area and the row as high as ever, and the text still in `aria-valuetext` and in the tooltip. That element is marked `dir="ltr"`, so in a right-to-left page the prefix is still at the left of the number.
- **`direction` is not used.** The form hands every interface the direction of the text typed into the field: the form of an item that of the user (`app/src/modules/content/routes/item.vue:888`), a form inside the translations interface that of its language (`app/src/interfaces/translations/translation-form.vue:213`). The meter holds no such text, and like the stock Slider it runs in the direction of the page, which the logical properties of its styles follow without any code.
- **The interface is one area, as high as a stock input.** `.meter` is a column with a minimum height of `--theme--form--field--input--height` (54px in the default theme) which centres what is in it: the track, across the whole width, and 0.25rem under it one line with the caption at the start and the value text at the end. Nothing is laid out outside the area, so the note which the form prints under a field is where it is under an input, and the field takes the room of an input; only the large pieces up to the pointer are drawn past it, by up to 3px, and only under a caption which wraps. A caption which wraps makes the area grow. With no caption the text is alone at the end of the line; with the text off the caption is alone; with neither there is no line and the track is in the middle. No border and no background. The track is 0.75rem high with rounded ends, in the colour token of the stock Slider's line; the fill is a block at its start, sized along the inline axis.
- **The line gives the caption what the text leaves.** It is a flex container: the text keeps its width (`flex: none`) at the end (`margin-inline-start: auto`), the caption takes the rest and wraps, so the text stands at the end of the caption's first line. The caption asks for 4rem before it gives way (`flex: 1 1 4rem`); where the field has no room for that and the text together, the line wraps and the text goes under the caption, still at the end and still whole.
- **Five ways to draw the track, under the key `visualization`.** `contiguous` is the one bar and the default. `pills`, `segments`, `bars` and `dots` cut the track into pieces which are each filled or not. `readLook(own, inherited)` reads the word, the number of pieces which is wanted (`subdivisions`), the layout of the dots (`dotsLayout`), the two colourings (`activeColoring`, `inactiveColoring`), the number `grow` (`growOf`) and the switch `fade`, apart from `readOptions`, with the fall-back of the limits: the first usable value among the entry's own options and the interface's, so a missing, an emptied (`null`) and a broken one all fall through. `grow` alone is read from the entry's own options only. Any other word is the default. `Options`, `Reading`, `readOptions` and `readingOf` know nothing of any of it.
- **The key is `visualization` and not `style`.** Options arrive as props, and Vue binds an attribute called `style` to the element instead of handing it over.
- **How many pieces: wanted, capped by what fits** (`pieceCount`, which is `drawnCount(wantedCount, fitCount)`, with the divisors for pills and segments only).
  - **Wanted** (`wantedCount`): `subdivisions` when it is a whole number or the text of one, 2 where it is less, with no largest. Otherwise `max - min`, after the fall-back and the ordering of the range, when that is a whole number of at least 2. Otherwise nothing in particular (`null`).
  - **Fit** (`fitCount`): `floor((width + gap) / (piece + gap))` with the smallest piece and the gap of the visualization in its place, from `PIECE_SIZES`: in the form pills 20 and 4, segments 14 and 3, bars 4 and 2, dots 12 and 4; in the display pills 8 and 2, segments 6 and 2, bars 2 and 1, dots 6 and 2. The dots' gap went from 6px to 2px, when the owner wanted more of them, and then to 4px, when at 2px they stood too close (1.5px, 1px and 2px in the display); 4px is also what lets a dot up to the pointer be drawn a pixel larger on every side with two pixels left. A range of a hundred draws 21 dots in half of the form, 44 across it and nine in the display, packed or spread. These are pixels at 16px to the rem, and the styles of the two components draw the same gaps and dots in rem: change one and the other together.
  - **Drawn** (`drawnCount`): what is wanted where it fits; else the largest number of at least 2 which fits and divides it (100 with room for 29 is 25, 12 with room for 7 is 6); else, for a prime and for nothing wanted, as many as fit; and 0 where fewer than two fit, which makes the meter one bar.
  - **Bars have no divisor rule** (`drawnCount(wanted, fit, false)`): what is wanted where it fits, else as many as fit. And what fits is counted in device pixels (`fitCount` with the ratio): the least bar and the least gap of `PIECE_SIZES`, each rounded up to a whole device pixel, in the whole device pixels of the width. So a range of a hundred in 342px draws 57 bars at ratios of 1, 1.5 and 2 (4px and 2px, which are whole device pixels at all three; 53 at 1.25, where they are not), and the display 24, 22 and 24. The least bar of the form was 3px, which gave 68; it is 4px because that is the bar the owner had seen and liked on fifty bars, and asked to keep (decided by the coordinator for the owner; it is the one number `PIECE_SIZES.form.bars.piece`, should 3px be wanted back). It drew fifty, the largest divisor of a hundred which fits, until the bars got whole pixels: fifty equal bars then left 44px of the 342px empty, which the owner saw and did not want. A divisor makes every bar a round share of the range; a row which ends where the field ends was wanted more. Pills and segments keep the divisor rule: they share the width to the last fraction and leave nothing over.
  - **Dots have no divisor rule either, in either layout.** Packed dots keep their size and their gap and stand from the start, so twenty dots for a hundred left 64px of 342px empty at the old gap, which the owner saw as dead space after the dots. As many as fit leaves less than a dot and its gap: 10px behind 21 dots in 342px, 13px behind 44 in 713px, 2px behind the display's nine. A number which is wanted and fits is a short row from the start, which is what packed means. Spread dots reach the end of the track whatever their number, and kept the divisor rule for one follow-up; with the wider gap that made them sparse (25 across the form where 44 fit, five in the display where nine do), so they are as many as fit too. Packed and spread dots are therefore always the same number for the same field and width, and differ only in where they stand; `pieceCount` does not look at the layout. Packed dots and their gaps are whole device pixels at ratios of 1, 1.5 and 2 and are drawn alike there (measured); the gaps of spread dots are what `space-between` makes of a width which does not divide, and differ by one device pixel (4 and 5 for 21 dots in 342px).
  - **One cap for the whole package,** `MAX_PIECES`, 200, on what fits and so on what is drawn: every piece is an element.
- **The look depends on the width, and that is decided.** The fixed limit of ten pieces which an earlier draft had is gone. The same field has ten pills in half of the form, 25 across it and five in a table. Whoever wants the same everywhere sets a small number.
- **The form measures, the display does not.**
  - **The interface** has a `ResizeObserver` on the element on the line of the track, which is the track of the one bar or the row of pieces: one element in both cases, so the reference stays. The form gives it its width (it is a stretched item of the column), never what is in it, so the count cannot feed back into what is measured. It is measured once in `onMounted`, so the first frame is right, and the observer is disconnected before unmount. The width is in a `shallowRef` which only the computed `count` reads; a computed value which comes to the same number does not wake what depends on it, so the template is rendered again only when the count changes. Do not read the width in the template or in anything which draws: the gradient is laid out without it for that reason. Two browser tests pin the two rules: a `MutationObserver` sees nothing change in a meter whose width changes within one count, and a list of the page's `ResizeObserver`s loses the one of a meter whose field leaves the form.
  - **A field without a width,** in a tab or group which is not shown, fits none: it draws the empty one bar, which keeps the height, and is measured again when it is shown.
  - **The display** hands `DISPLAY_WIDTH`, 72, to the same function. Its bar has that length in every row, so 7 pills, 9 segments or 9 dots fit, always, and 24 bars, or 22 on a screen of one and a half device pixels to the pixel.
- **How many are filled** (`filledCount`): `Math.round(piecesAt(fraction, count))`, the cleaned product of the count and the fraction of the one bar, which is already within 0 and 1 (see below for the cleaning). The first that many are filled, completely; no piece is ever filled in part, and without `grow` or `fade` nothing marks a value just above the minimum as the dot of the one bar does. Only the drawing is rounded: the text, the tooltip, `aria-valuenow` and `aria-valuetext` are those of the real value.
- **Pieces which grow** (`grow`, the interface only). `grow` is a number: how many pieces in front of the fill can be growing at once, 0 for off, up to `MAX_GROW`, 20 (`growOf`: a number or its text; anything else, a boolean among it, and a negative number are 0). Above 0, every piece which is not filled is drawn small (`SMALL_PIECES`: a dot at half its diameter, a pill at six tenths both ways, a segment and a bar at their full width and a third of their height), and a piece which is about to be filled is as large as the value has come towards it. `growthOf(fraction, count, index, reach)` is that share: with the value at `fraction * count` pieces, not rounded but cleaned of the dust of the product (`piecesAt`), a piece is filled once the value has come half of it, which is where its growth is 1; a piece which is still `d` pieces from that has grown `1 - d / reach`. `pieceScale` turns the share into a size and `scaleCss` into `scale(along, across)`, which the component puts on the piece as an inline `transform`: about its middle, so the piece stays on its place and no box changes, and with fractions, so no size is rounded to a pixel. The pitch, the gaps, `pieceGeometry`, where the pointer counts a piece and the height of the area are what they are without it. A filled piece has no transform from it, a meter without a value none anywhere, and one bar ignores the option. (The pieces up to the pointer have a transform of their own while it is there, with or without `grow`: see the marks.)
  - **The reach in pieces** (`reachOf`) is `grow / 2` up to 1 and `grow - 0.5` above it. With 1 it is the last half piece before a piece is filled: only one piece is ever growing, and at a whole number of pieces none is. With 2 it is a piece and a half: the next piece is always partly grown and the one after it starts as the next comes close to being filled. With 3 a ramp of up to three, and so on. Below 1 the growth starts later than half a piece before the fill.
  - **Thin bars reach further:** at least `BAR_REACH` pixels of the track for each 1 of `grow` (15 in the form, 9 in the display: two and a half bars at their narrowest in the form, three in the display), counted by how far the bars are apart as they are drawn (`barFit`), where that is more than the pieces give. Fifty bars for 0 to 100 are two units each and a hundred are one, so no whole value ever lies in the last half of a bar, and by the pieces alone such bars were never seen growing (measured: at 0 of 101 whole values, where twenty segments showed a growing piece at 40; reported by the owner). With the longer reach the next two or three bars are a ramp, each further along the nearer it is to being filled, at every value which leaves a bar to fill. That part of the reach is counted in half pieces (`round(2 * grow * px / pitch) / 2`), so like the count it changes now and then and not with every pixel of the width, and the component asks for it only where the look grows or fades: a meter without that is still drawn again for its count alone.
  - **The reach grows out of the start of the scale.** What counts in `growthOf` is `min(reach, pieces + 0.5)`, the position in pieces plus the half piece which fills the first one. At the minimum that is half a piece, exactly as far as the first piece is from being filled, so nothing has grown: an empty meter is empty. As the value rises the ramp gets longer with the fill, piece i being `(2p - i) / (p + 0.5)` along while the whole reach is not there yet, until it is; from then on the values are those of the plain rule. It is continuous everywhere, which a unit test sweeps in thousandths of a piece. It replaced a rule which made the minimum a case of its own ("nothing is under way there"): with a long reach the whole ramp then stood in front of the first filled piece at the first value and was gone at the minimum, which the owner saw on bars with a `grow` of 4 (nine bars larger than small at 1 of 100, none at 0). A reach of half a piece or less is never cut short, so a `grow` up to 1 on pills, segments and dots is untouched. Thin bars have more than that also with 1, by their pixels, so their first two values changed too: at 1 of 100 in fifty bars a bar is filled and none is on its way, at 2 the next is two thirds along.
  - **Pieces which only fade in have the reach of 1,** and with a `grow` above 0 the reach of that number. The display has no `grow`, so its fading always has the reach of 1.
  - **`filledCount` rounds the cleaned product too.** It used to round `fraction * count` as it came: `0.29 * 50` is 14.499999999999998, and 29 of 100 in fifty bars filled 14 where half way up is 15. The ramp made that visible, as a bar at its full size which was not filled.
  - **While the pointer drags the value, the growth is counted from where the pointer is** (`exact` in `interface.vue`, handed to `drawingOf` as `ahead.at`): the share of the track under the pointer for `position`, the value before it goes to the grid for `relative`. Counted from the value, a piece passed through only as many sizes as there are steps in its reach, two for a segment of five units, each a jump since a drag has no transition (measured over a slow drag: 2 sizes, and 68 from the pointer's place; reported by the owner as choppy). What is filled, the colours, the text and what is written stay those of the value. `piece` input is left out: there the value moves by whole pieces. At the release `exact` is cleared and the sizes ease to what the value gives.
- **The display never grows pieces.** They are too small there. `readLook` takes `grow` from the entry's own options alone, the form of the display has no such option, and `display.vue` hands `drawingOf` a look with `grow: 0` whatever it read.
- **The piece which fades in** (`fade`, both entries, with the usual fall-back). The same share, over the same reach, so thin bars fade in over their ramp too: a piece which is not filled has an `over` in its drawing while that share is above 0, which is the paint this piece has once it is filled, by `activeColoring`, and the share as its opacity. The component draws it as one child of the piece (`mt-over`, `md-over`) which covers it, without pointer events, and the piece gets `mt-under` (`md-under`) to be its containing block. Under it the piece is what `inactiveColoring` gives it. At the moment the piece is filled the two are the same, so no colour jumps. A gradient which only the fading piece shows still gets its stops. Every other piece has no child, and a meter which does not fade has none anywhere.
- **Where the pieces are is plain data** (`pieceGeometry`): the start and the end of every piece in pixels from the start side, for a shape, a place, a count, a width and a layout of dots. Nothing draws from it: the styles lay the pieces out by the same rules (flex with a gap, `space-between`, or for bars the two sizes of `barFit`). The pointer finds the piece under it by this data, and the end of the last piece is the length which stands for the whole range where the pointer sets the value by its place: for packed dots and for bars that is before the end of the track, so a press in the empty rest is a press past the end.
- **The pieces in the form.** The row (`mt-strip`) stands where the track stands, at its height, and carries the role and the values as the track does; the line under it and the area around it are untouched. It is a flex container, so the first piece of the document is at the start side in either direction. Pills and segments share the width equally; bars are each as wide as `barFit` says (see below). Pills (`mt-pills`) are 0.25rem apart and round at both ends. Segments (`mt-segments`) are 0.1875rem apart and square, but for the start of the first and the end of the last, by logical corner properties, so the row reads as one rounded bar which is cut. Bars (`mt-bars`) are 0.125rem apart and square. Dots (`mt-dots`) are circles as high as the track which do not stretch: 0.25rem apart from the start, or with `mt-spread` from edge to edge by `space-between`. Without a value every piece is a dashed outline like the track's (`mt-empty`).
- **Bars are drawn in whole device pixels** (`barFit`, in both entries). Bars which share the width come to a fraction of a pixel each (342px for fifty is 4.88px), the browser puts every edge on a whole device pixel, and some bars are then a pixel wider than others (measured through a row of pixels: 4 and 5 mixed at a ratio of 1, 7 and 8 at 1.5, 9 and 10 at 2; reported by the owner). So a bar and a gap are each a whole number of device pixels. `barFit(place, count, width, ratio)` tries every gap from the least one (that of `PIECE_SIZES`, rounded up to a device pixel) to twice that, with the widest bar of which the count then fits, and takes the pair which leaves the least of the track empty, the narrower gap where two leave the same: five bars in 342px are 66px with gaps of 3px and end at the field's end, where gaps of 2px would leave 4px. The component hands both to the row as custom properties (`--mt-bar` and `--mt-gap`, class `mt-fitted`; `--md-bar-size`, `--md-gap` and `md-fitted` in the display), the bars are `flex: none` at that size, and what is left of the track is empty at its end side.
  - **The ratio** is `devicePixelRatio`, from `useRatio` in `ratio.ts`: one reactive value for the whole page with one listener, a media query for the ratio as it is, asked again after every change, so a zoom of the page and a move to another screen are followed and no row of a table watches anything.
  - **The two sizes are numbers** which change only when a bar gets a device pixel wider, so like the count they do not wake the drawing with every pixel of the width. They are the one place besides the count where the measured width is read.
  - **Neither size is ever less than the least one the count rule assumes,** since that rule counts with the same least sizes in device pixels: 4px are 5 device pixels at a ratio of 1.25 and a gap of 2px, 2.5 there, is 3. `barFit` asked for more bars than fit, which no caller does, makes them thinner, down to a device pixel, and then gives up.
  - **The leftover, where as many bars are drawn as fit,** is less than one bar and its gap: at most 5px at ratios of 1, 1.5 and 2 (a sweep of every width from 120px to 1200px), and 1px, nothing and 1px in the display. The owner's case, a hundred in 342px, leaves 2px behind 57 bars at all three.
  - **The leftover of a number which is wanted and fits can be more than a little.** That number is drawn as it is (`subdivisions`, or one bar for each unit of the range), and its bars are all alike, so up to one device pixel for each bar is left: fifty bars set in 342px leave 44px at a ratio of 1 (bars of 4px; 5px do not fit), 10.7px at 1.5 and 19px at 2; in the form's widths up to 716px the most is 100px (102 bars in 710px, a seventh of it) at a ratio of 1, 70px at 1.5 and 54px at 2 (a tenth at most at both); the display leaves up to 16px of its 72px (19 bars) at 1, 10px at 1.5 and 7px at 2. The wider gaps help some widths (a hundred bars in 697px are 4px with gaps of 3px and leave nothing, where gaps of 2px would leave 99px) and not others. The same goes for a field in which more than 200 bars would fit, from 1198px: it draws 200, which leave up to 198px (of 1396px). The owner accepts this for now. Bars and gaps are never made unequal to use the room up; what is left to try is the room split to both sides, or a nearby count which fits better.
  - **A page which is only told a ratio is not a screen which has it.** A browser context with a `deviceScaleFactor` is laid out in whole CSS pixels and enlarged afterwards: there a bar of 4.5px is drawn as 4 and 5 by turns, whatever the code does. Only a browser started with `--force-device-scale-factor` and no viewport has real device pixels. The browser tests of this start one for each ratio.
- **The pieces in the display.** The row (`md-strip`) is an inline flex container in the place of the bar, one unbreakable piece like it and as long as it, and the role stays on the root. Pills and segments are 0.125rem apart, bars 0.0625rem, with the corners as in the form at the display's height. Dots are 0.375rem across, smaller than the bar is high so that nine fit. Packed (`md-packed`) they are 0.125rem apart and the row is as long as its dots; the root is told that length (`--md-bar`, set inline) because the room of the text is worked out from it. Spread (`md-spread`) they take the length of the bar.
- **Colouring: a colour for a value, or a colour for a place** (`drawingOf`, which both components draw from).
  - **The stops** (`scaleStops`): the colour of a meter at its minimum, at 0, and every threshold above the minimum at its share of the range, in rising order. A threshold beyond the maximum is beyond 1 and stays in the list: CSS takes a stop outside the box. Fewer than two stops means one colour, and every colouring is drawn as `value` then.
  - **`value`:** the colour of the reading, as before, as an inline `background-color`.
  - **`blend`:** one colour as well, for the fill and for every filled piece: the colour the gradient has at the place of the value (`blendAt`: the two stops around the place and the share between them; `blendCss`: `color-mix(in srgb, <from> <100 - share>%, <to>)`, mixed by the browser because a stop may be a theme variable). The place is that of the stored value, which `drawingOf` is handed as its fifth argument, so a value beyond the range blends on towards a threshold beyond it. On a threshold and from the last one on it is that threshold's colour. As the colouring of what is not filled it is the same colour, faded.
  - **`steps`:** a piece has the colour of the value it reaches when it is filled completely (`valueAtPiece`, which multiplies before it divides so that the 57th of a hundred reaches 57). The one bar has a gradient with two stops at every threshold, so the colour changes at once.
  - **`gradient`:** the stops as a CSS gradient across the whole track, of which every surface shows its own part. The surface has the class `mt-paint` (`md-paint`): its background is `--mt-n` times as wide as itself and placed at `--mt-at`, from 0 for the first part to 1 for the last, which as a percentage of `background-position` moves the image by that share of what it is wider than the box. A piece is one of `--mt-n` equal parts, with the gaps between pieces not counted, so nothing depends on a measured width. The fill of the one bar is not sized by `--mt-n`: its image is as wide as the track itself, `100cqi`, with the track made a size container where its fill is painted so (`mt-scaled`); in the display it is the bar's 4.5rem. The blend is never squeezed into the fill, and no stop can move.
  - **A place keeps its colour to the pixel while the value changes.** The fill of the one bar used to have an image `1 / fraction` times its own width, which is the width of the track only in exact arithmetic: at each value it came out a fraction of a pixel wider or narrower, and the place where one colour ends jumped between two pixels during a drag (seen: 136 and 137 in a track of 342px). Never size a painted surface by something which changes with the value. `--mt-n` is still set on the fill, for a browser which does not know the unit and drops the declaration. Pieces never had this: their sizes do not depend on the value.
  - **What is not filled** (`inactiveColoring`): `plain` is the track of the styles. Otherwise one of the four ways (`value`, `blend`, `steps`, `gradient`), or `automatic`, which is the way of what is filled, and faded.
  - **Faded** (`fadedColor`, `FADE`): `color-mix(in srgb, <colour> 30%, <the track's colour>)`, seven parts of the track in ten, in every theme. The browser mixes, because a colour may be a theme variable; script never computes a colour. Chosen by eye: at 30% the hue still shows on the light and on the dark track, and the filled part stays clearly stronger.
  - **The stops reach CSS in two custom properties on the root,** `--mt-stops` and `--mt-weak-stops` (`--md-…` in the display), and a faded surface has a rule of its own which reads the second (`mt-weak`). It must not set `--mt-stops` for itself: the fill is inside the track and would inherit the faded stops (seen).
  - **A gradient has no logical direction.** `to right` is mirrored for a right-to-left page by `:dir(rtl)` rules, which also count the place from the right. The app writes `dir` on the root element.
  - **No value has no colours:** `drawingOf` returns nothing to paint, and the dashed look stays.
  - **Every colour in a stop list went through `isColor`,** as it is or inside the one `color-mix`.
- **A field which sets none of the new options is drawn as in 1.0.1,** element for element: no `style` on the root or the track, the classes `mt-track` and `mt-fill` alone, the colour of the reading inline on the fill. A browser test reads those attributes.
- **Every option is always in the options form; eight of them show only while they apply.** `subdivisions`, `dotsLayout`, `grow`, `fade`, `prefix`, `suffix`, `sensitivity` and `step` have `meta.conditions`, and all but `step` `meta.hidden`, on the values of the form itself (`visualization`, `indicatorFormat`, `input`), which the app's form evaluates wherever it draws the options. `prefix` and `suffix` are hidden while the format is the percentage, which has neither; `step` is hidden by the input method `none` alone, and `sensitivity` shown by `relative` alone. `hidden` is what holds while the deciding option is not among the form's values: for the display, by the visualization of the interface, so a display whose own visualization was emptied shows them by the interface's. A rule has exactly one key, or the app passes it over (`applyConditions`). A value which was stored stays stored while its input is hidden, and is ignored. The placeholder of the number of subdivisions is the app's own "Automatic" (`$t:automatic`, which the form translates in a placeholder too; seen), or the interface's number in the form of the display. `grow` is in the form of the interface alone, as a number input in steps of a half; `fade` is a toggle.
  - **Never leave an option out of the list by what the field holds.** The form used to be built from the options as they were being edited. The ordinary field settings hand the options function the field with its options and type, but `system-interface-options`, which draws the options of an interface inside another form, calls it with `props.context?.() ?? { field: { type: 'unknown' }, ... }` (read in the built app of 11.17.4), and the dialog of a stock Repeater's field gives it no context. There the function saw no options, decided every time that the three did not apply, and they could not be reached at all (seen, and reported by the owner).
  - **The same stand-in has no type and no limits.** The Step input is a decimal one there also for a whole type, and its placeholder, which in the field settings is what an empty step comes to for the type and the limits as they are being typed (`own`, the fifth argument of `optionFields`), is the app's "Automatic" there (`known` is false). The component rounds the step for a whole type at run time, when the form of the Repeater's row does say the type.
  - **That dialog has a display, in a group which starts closed** (`group-display`, with `display` on `system-display` and `display_options` on `system-display-options`; read in the options of the `list` interface in the built app, and seen). What is chosen there is stored in the sub-field as `meta.display` and `meta.display_options`. A row of the Repeater is drawn by `render-template`, which takes the display of the sub-field, or else the default display of its type, the plain number, and hands it `display_options` as its options and `meta.options` as `interfaceOptions`: so the row follows the display's options from the dialog, and the interface's for what those leave unset, as a table does. An earlier note here, and a reply to the owner, said the dialog had no display: the group was closed and its fields were not in the page.
  - **The form of the display gets the stand-in too, and is told so** (`known`, the fourth argument of `optionFields`: `display.ts` passes whether the field it was handed has a `meta`). Without the field the options of the interface are not to be had, and the form used to show plain defaults as if they were the interface's: a maximum of 100 where the interface had 1, "Contiguous" where the row drew the interface's pills, with the number of subdivisions hidden. Not told its field, the form claims nothing: the placeholders say "As in the interface", the dropdowns have no default, and `subdivisions`, `dotsLayout` and `fade` show until the form's own visualization rules them out, `prefix` and `suffix` until its own format does. The two toggles keep a default, since a toggle cannot show "not set".
  - **A fixture for it needs the key and the type twice:** the dialog stores `{ field, name, type, meta: { field, type, interface, ... } }` and reads the two from `meta`; a definition without them shows an empty key and type.
- **The dropdowns of the display can be emptied.** `visualization`, `dotsLayout`, `activeColoring` and `inactiveColoring` have `allowNone` in the form of the display, which adds the app's "Deselect" to the list and stores `null` (seen). `null` falls back like a missing key, and the dropdown then shows what it comes to as its placeholder. In the form of the interface they cannot be emptied: there is nothing to go back to.
- **A fill is never narrower than the track is high.** The smallest value above the minimum shows as a dot, not as a sliver of a rounded corner. At exactly the minimum, and below it, there is no fill element at all.
- **Tracks are always as wide as their field,** whatever the text beside the caption says, so tracks one above the other end at the same place.
- **The text of a number is whole, or it is not shown.** Never a part of it: a part reads as another number, whether it is the first digits ("5" for 50%, "999,…" for 999,999,999,999,999), the last ones or, of a fraction in Arabic digits, the maximum alone, and an ellipsis does not mend that. So nothing cuts a number, in any script or direction, and there is no code which knows about either. Both components let the text wrap to a second line which is cut off.
  - **In the interface** the text has a box of its own on the line under the track, as in the display: a flex container which may wrap, one line high (1.25rem, the line height of that line), no wider than the field (`max-inline-size: 100%`), with `overflow: hidden`. Its first item is a space without a width (`::before`, U+200B), which holds the first line; the number is the second, and wraps away when the field is narrower than the number. The box keeps its line even then, so a field which is that narrow has an empty line where the text would be.
  - **In the display** the bar cannot be the thing which holds the first line, since bar and text have to stay two pieces of a template's line. The text has a box of its own: an inline flex container which may wrap, one line high (`1lh`, with `1.25rem`, the line of a table cell, for a browser without the unit), with the room the bar and the gap leave (`100% - var(--md-bar, 4.5rem) - 0.5rem`, so more beside a short row of packed dots), and `overflow: hidden`. Its first item is a space without a width (`::before`, U+200B), which holds the first line; the number is the second, and wraps away when it does not fit.
  - **That box is a flex container and not an inline block for the sake of the line.** An inline block which cuts its content sits on the line by its lower edge and not by the line of its text, which makes the line taller and the number stand too high beside other text. A flex container sits by the first line of its first item, here the space. Chromium, Firefox and WebKit agree on that (measured).
  - **What is left out can still be had.** The display's tooltip always has the value text (`tooltipOf`), after the caption when there is one, and `aria-valuetext` has it in both components.
- **No value has its own look.** `reading.empty` puts `mt-empty` on the root: the track loses its background and gets a thin dashed outline in `--theme--foreground-subdued`, and the text is a dash. The outline is not in the colour of the track, which is 1.2 to 1 against the page and too faint for dashes. A value which is not a number is treated as no value in the interface.
- **Forced colours have rules of their own, in CSS alone** (`@media (forced-colors: active)` at the end of both style blocks). Everything of a meter is painted with backgrounds, and a contrast theme of the system makes every background the colour of the page and drops gradients: without the rules nothing was left of a meter but its text (seen in the sandbox with Chromium's emulation, `page.emulateMedia({ forcedColors: 'active' })`: track, fill and pieces all computed to the page's colour, in the form and in the table).
  - **What is drawn there:** the track and every piece which is not filled are a 1px outline of `CanvasText` around `Canvas`; the fill, a filled piece (with its outline) and what is laid over the piece which fades in are `Highlight`; no value keeps its dashes, in `GrayText`; the handle is `Canvas` with an outline of `CanvasText`, one pixel higher because the track has a border there; the focus ring is `Highlight`. So filled is told from not filled by the colour and, where a piece is wide enough for an outline to leave a middle, by solid against hollow. The bars of the display, 2px wide, are all outline: there it is the colour alone.
  - **The colours of the options and of the thresholds give way,** which is what the mode is for: the rules are `!important`, since the colour of a fill or of a piece is an inline style. A system colour is left alone by the mode, so no `forced-color-adjust` is needed. Gradients are set to none as well, for a browser which keeps them.
  - **No size changes:** the track and the pieces of the form are border boxes already, and those of the display become border boxes inside the same rule. The large pieces up to the pointer, `grow` and `fade` are transforms and an opacity and work as they are; a small piece has a thinner outline, which still reads.
- **Print keeps the bars:** both roots have `print-color-adjust: exact` (and the `-webkit-` name before it), which is inherited, so every painted element asks the browser to print its background. Without it a printed form or table has the texts and no bars. A stock element computes `economy`, which a browser test reads beside ours.
- **Three transitions, and no other.** The third is that of the pieces up to the pointer (`mt-swell`, described with the marks above): their transform and, for a pill, its corner radii, over the same 150ms, while pieces are large and until the last has eased back. The other two: the size of pieces which grow and the opacity of the piece which fades in change over 150ms when the value changes by a press, a key or from outside. The rule is on the class `mt-eased` of the row, inside `@media (prefers-reduced-motion: no-preference)`. The class is there only where the look grows or fades, only from two frames after a value was first drawn (`eased`), and not while the pointer is moving the value (`following`, set at the first write of a move and cleared when the press ends): the form hands every interface `null` until the item has loaded, so a transition from there would play on every page load, and during a drag the pieces follow the pointer at once. A press itself eases, and a transition which is under way when the next change comes is taken up by the browser from where it is. During a drag the sizes are worked out from where the pointer is, so they change with every movement and need no transition; at the release they ease to what the value gives. What lies over a piece appears and goes with the piece it belongs to, so it eases only while it stays. The display has none, and nothing else in the interface has one but the pieces up to the pointer.
- **The role is on the track:** `slider` with `tabindex="0"` and `aria-orientation` where the field can be edited, `meter` where it cannot, both with `aria-valuemin`, `aria-valuemax`, `aria-valuenow` (the value kept within the range) and `aria-valuetext`. A slider says the range which can be written and the value within it, and where the field has no value the least of that range, since a slider has to have a value; a meter says the range as stored, and no value where there is none, as in 1.0.1. `aria-valuetext` is the text beside the bar, whether or not it is drawn, and the app's `no_value` for a field without a value. It is named by the caption through `aria-labelledby`, else by the name of the field (`fieldData.name` in the interface, the app's store of fields in the display), else "Meter". The visible text of the interface is `aria-hidden`, so it is not read twice; in the display the text is a child of the meter, which assistive technology does not read into.
- **The display is inline, with two atomic pieces.** Its root is an inline `span`, as the stock text display is, so in a display template it is part of the line. A table cell is a flex container, which makes the root a block as wide as the cell allows; only then do its own `overflow` and `white-space` apply. The track is an `inline-block` of 4.5rem which never shrinks; as the first thing on its line it is clipped by a cell narrower than itself. The text is the box described above. In a display template each of the two is one piece which the template's ellipsis replaces when it does not fit the line. The gap between bar and text is a margin of the track, because the number has a direction of its own. A value which is not a number is plain text in the same root (`md-plain`) and is cut like any other text, with an ellipsis.
- **The display never gets `null`.** The app draws its own placeholder for it (`app/src/views/private/components/render-display.vue:25`). A value which is not a number is shown as plain text, and blank text as the app's placeholder (`value-null`).
- **The options form is one function for both entries** (`optionFields`). It is a function of the field in both, and shows what an option which is not set comes to: for the display the options of the field's interface, as the placeholders of the limits and of the caption and as the `default_value` of the other inputs; for the interface the limits a Slider left behind. A default which a form shows is not stored, which is what keeps the fall-back in place, and it is shown only while the key is missing, which is why an emptied colour or list means none (see the fall-back above). The display's form starts with a notice which says all of this in three sentences, a field of the type `alias` with `no-data`, which stores nothing. The limits are `float` so that the inputs hand over numbers; a `decimal` input would store their text (`app/src/constants.ts:171-173`).

## Invariants: do not break

1. **Stored values and option keys are public API.** The field holds a plain number, which the display never writes and the interface only as a number on its grid of steps. `input`, `step` and `sensitivity` of the interface keep their names and meanings once they are released, as do the five words of `input`, `automatic`, `position`, `piece`, `relative` and `none`; `stepInterval` keeps being read as the step. The ids `meter` (interface) and `meter` (display), and the option keys `min`, `max`, `label`, `indicator`, `indicatorFormat`, `prefix`, `suffix`, `visualization`, `subdivisions`, `dotsLayout`, `grow`, `fade`, `color`, `thresholds`, `activeColoring` and `inactiveColoring` with the keys `value` and `color` of a threshold, keep their names and meanings once they are released, as do the three formats `percent`, `value` and `fraction`, the five visualizations `contiguous`, `pills`, `segments`, `bars` and `dots`, the two layouts `packed` and `spread` and the words of the two colourings. `minValue` and `maxValue` keep being read as limits.
2. **Read loosely.** Limits and thresholds arrive as numbers or as their text, and a `decimal` or `bigInteger` value as text on some databases. Options which were stored by another interface or by hand must keep working: `min: "0"`, `max: "12.5"`, `indicator: true`. A display which has options of its own draws by them, whatever its interface has: the browser test of the fields `apart`, `muted` and `rated` pins that.
3. **The options form of the display shows what the layouts draw.** Whoever changes the fall-back of a key changes what the form shows for it, and the other way round. An option which was never set arrives as `undefined` and an emptied one as `null`; do not give a prop a default, which would hide the difference.
4. **The defaults are in the components, not in the form.** Options arrive as stored, and a default which the options form shows is not stored. `indicator` defaults to on. Do not type a prop as a boolean: Vue would turn a missing one into `false`, and the display's could then not fall back.
5. **Never throw, never hand the page a number which is not finite.** See "How it works". Keep the unit test which pins it.
6. **Nothing falls through.** `inheritAttrs: false` in both components, and no template binds `$attrs`: the form passes some twenty props and two listeners to every interface, and a layout a handful to every display.
7. **The options are untrusted.** Text reaches the page only through `v-text`, the prefix and the suffix as part of the one string of the value text. A colour reaches CSS only after `isColor`, which takes a hex colour or one `var(--theme--...)` and nothing else, so there is no room for a second declaration or a `url()`.
8. **`meter.ts` stays free of Vue, the DOM library and Directus,** and `options.ts` of everything but a type of Directus. `tsconfig.test.json` type-checks both without the DOM library.
9. **A field which cannot be edited never emits, and is the meter of 1.0.1.** No dimming for `disabled`, no pointer reaction, no tab stop, no listener, no handle. A meter whose input method is `none` is such a meter, by `canEdit` and by nothing else: never give a handler or a style a check for the word. A field which can be edited never writes anything but what `snapValue` or `keyValue` made: a finite number on the grid, within the range, whole for a whole type. A finger which goes straight into a scroll of the page has written nothing (one which drifts sideways first has, and it is put back: a known gap). No transition in either, but for pieces which grow or fade in and for the pieces up to the pointer.
10. **`contiguous` with the default colouring is the meter as it was.** Whatever is added must leave its markup, its styles and its tests alone. A piece is filled or not, never in part, and what is said about the value is never the rounded one. `grow` and `fade` change how the pieces which are not filled are drawn and nothing else: no box, no count, no value, and with both off a meter has the elements, classes and inline styles it had before there were such options. The pieces up to the pointer are the one thing beside them which sets a size, and only while the pointer is on a meter which is filled by the piece; with no pointer there, such a meter too is as it was. The number of pieces comes from the width of the track's own line and from nothing which the pieces could change.
11. **A number shows whole, or not at all.** Never a part of it, in any script or direction, with or without an ellipsis: what is left would read as another number. No `text-overflow` on a number, and no box which can cut one in the middle.
12. **Bundle hygiene.**
   - The root `AGENTS.md` has the rules. There are no dependencies to bundle, and none should be added. `vue-i18n` in particular is not imported: `src/i18n.ts` reads `$t` and `$i18n` from the app.
   - `dist/app.js` is about 49.6 KB (15.5 KB gzipped; 13.7 KB in 1.0.1, 25.4 KB with the pieces and the colourings, before the editing, 36.1 KB with the editing, 38.1 KB before the pieces which grow and fade in, 46.6 KB before the prefix, the suffix, the default step and the styles for forced colours, which are about 1.2 KB of the 3 KB) and `dist/api.js` 72 bytes. Report size changes.
   - **No comments in the `<style>` blocks.** The build keeps them in the bundle, so what the styles rely on is written at the end of each component's script, which is not shipped, and under "How it works" here. `grep -o '/\*' dist/app.js | wc -l` is 0 after a build.
13. **It is an app-only bundle,** so the Marketplace can install it under the default `MARKETPLACE_TRUST`. Don't add API entries casually.
14. **Directus look.** Only `--theme--*` tokens for colours: the track in `--theme--form--field--input--border-color`, as the stock Slider's line and progress bar, the fill in `--theme--primary` unless an option says otherwise, the text in `--theme--foreground`. Styles are scoped; class names other than the two roots (`meter`, `meter-display`) start with `mt-` in the interface and `md-` in the display.

## Code style

The root `AGENTS.md` has the style of the repository. In this package also:

- The unit tests cover `meter.ts` and the list of fields which `options.ts` builds. Everything in the two components, and what the app makes of the options form, has to be checked in a browser.
- The names of the options are the app's own strings where one says exactly the same (`$t:interfaces.input.minimum_value`, `$t:interfaces.input.maximum_value`, `$t:label`, `$t:format`, `$t:color`, `$t:automatic`, `$t:displays.formatted-value.prefix` and `$t:displays.formatted-value.suffix`, which are the names of the same two options of the stock Formatted Value display, and `$t:percent` and `$t:value` for two of the formats). "Value Text", "Thresholds", "Value / Maximum", "Visualization", "Subdivisions", "Dots Layout", "Grow", "Fade In", "Active Coloring", "Inactive Coloring" and "Input Method" with their choices ("By position", "By piece", "None" among them) and the notes have no such string and are plain English; the placeholder of the number of subdivisions is the app's `$t:automatic`. Things which are easy to trip over:

- **A click right after a page opens lands on a cover.** The app fades out an element over the whole page (`.hydrating`) for a moment after the form is there. `openEdit` in the spec waits until it is gone.
- **The app keeps a list of the keys which are down,** for its shortcuts. A `keydown` which a test sends to an element without a `keyup` stays in that list, and Ctrl+S no longer saves. `keyOn` in the spec sends both.
- **Home, End and the Page keys scroll the page** when no meter has the focus, and the scrolling goes on for a moment. The test of the read-only field sends them to the element instead, and measures the two twins in one `evaluate` each.
- **A field with an odd number of half-width fields before it starts a row at the right.** The twins of the spec have an even number before them, so they are one row.
- **The pointer lock cannot be had in the browser of the tests.** A test of its own starts the full browser for it (`playwright.chromium.launch({ channel: 'chromium' })`), signs in as the fixtures do, and is skipped with the reason where that browser cannot be started, so a runner without it shows a skipped test and not a passed one.
- **The dialog of a Repeater's field is reached** through Settings, Data Model, the json field, Interface, "Edit Fields", and the row which names the interface ("— meter"). Its inputs are in `.extension-options`. It is saved by its own button and then the field's. Its display is in a group which starts closed: the fields `display` and `display_options` are not in the page until the divider of that group is clicked.
- **A click anywhere on the label of a field opens the menu of the field,** down to the last row of pixels of the label's box. The menu stays open, lies over the form under it and takes the next clicks; Escape does not close it, a second click on the label does.
- **`npm run sandbox:test -- meter/ -g "..."` loses the `-g`,** which npm takes for itself, and runs the whole spec. Run `npx playwright test meter/ -g "..."` in `sandbox/`.
- **A transition makes a size a moving target.** The tests of the pieces which grow read sizes with reduced motion emulated, and look at the transition apart: by the computed `transition`, and by counting `transitionrun` events on the row.
- **Packed dots are a short row.** A drag along a meter of packed dots goes along the row of dots, 76px for five, not along the width of the field.
- **The save shortcut does nothing while a drawer is still closing.** The Repeater test waits until no drawer is left.
- **A ratio which is emulated is not a real one.** `deviceScaleFactor` on a context enlarges a page which was laid out in whole CSS pixels; `--force-device-scale-factor=2` as an argument of the launch, with `viewport: null`, gives a page real device pixels. Screenshots of such a page are in device pixels, and `pixels()` in the spec returns that many for a row.
- **Where the pointer sets the value by its place on bars,** a test has to go by the row of bars and not by the track: the row ends before the track does.
- **The trace of a failed run is gone with the next run,** which empties `sandbox/test-results`. Copy the folder first. And do not build while a run is under way: the sandbox reloads the server's extensions when a `dist` changes (`EXTENSIONS_AUTO_RELOAD`), which can stall requests for a while.
- **A finger can be driven.** A context with `hasTouch`, `page.touchscreen.tap` for a tap and `Input.dispatchTouchEvent` through a CDP session for a finger which moves.
- **The handle lies over the colours near the end of the fill.** A test which reads the colours of the track from a screenshot keeps 16px away from the end of the fill, or reads a place which the fill is well past.
- **The listeners of `document` can be asked for like those of an element** (`documentListens` in the spec).
- **A row of pieces is measured in one go too.** `pieces()` in the spec reads place, size, colour and state of every piece in one `evaluate`; `expectFilledPieces` wants the filled ones to be the first of the document, whatever the direction.
- **A field with the width "fill" changes the columns of its whole form.** Half of the form is 342px in the spec's collection and 293px in a form which has such a field. That field is therefore in a collection of its own (`sandbox_meter_wide`): in the first one it made a text which the older tests count on no longer fit.
- **A field is squeezed by its `.interface`,** not by the `.field` around it, which does not get narrower than about 200px.
- **A resized window goes on settling,** so a test reads a width and a count together and again until they agree (`toPass`, with a time limit: without one it goes on until the test's own).
- **Colours are read from the page, not from the styles.** The computed style of a painted surface is the same gradient everywhere; `pixel()` in the spec takes a screenshot of one pixel and reads it out of the picture, and `colourOf` asks for the middle of an element or a share of its width. The expected colour of a blend or of a faded colour is worked out in the spec, and compared within a few steps of 255.
- **The form hands over `null` before the item arrives,** so a test first waits for the text it expects.
- **The smallest fill is 12px in the form and 8px in the display,** whatever the value. `expectFilled` in the spec knows it; a test of a small share has to as well.
- **Two questions about two boxes are two moments.** The End key and the space bar scroll the page, and the scrolling goes on for a while. `expectFilled` therefore measures the track and its fill in one `evaluate`; asked one after the other, the two were once 19px apart.
- **Right-to-left needs no user, but not the root element either.** The app writes `dir` on the root element again with every update of the document head. The spec's `turn()` sets it on `body`. That works because the meter follows the page and ignores the `direction` it is handed, which stays `ltr` in such a page.
- **An inline block which cuts its content sits on the line by its lower edge,** and so does one which merely holds a block that cuts. The line grows by a pixel or five and the text stands too high beside other text; a table cell of 20px hides it, a display template does not. The test of the related-values template compares the height of the letters.
- **A theme colour can only be read once the page has its theme.** `token()` right after `page.goto` gives the colour of the text, since the variable is not there yet. Read it after the first thing the test waits for.
- **A run of one test recreates the collections,** because `beforeAll` runs for it too. What the test of the emptied options saved is gone after it, so look at that state in a full run or set it through the API.
- **What shows of a text is worked out, not asked.** `shown()` in the spec takes the box of the number and cuts it by every element around it which hides its overflow, up to the cell or the field. A number which has wrapped to the hidden second line still has a box and its text; only that sum says that nothing of it shows.
- **The app's tooltip leaves `data-tooltip` on its element.** The display always has a tooltip now, so its root carries that attribute beside its own.
- **Arabic digits are narrower than western ones in the app's font.** The longest text of the spec fits half the form for an Arabic user and not for an English one; the Arabic test squeezes the field to 150px instead.
- **A test which changes the administrator's language restores it in a `finally`.** Every other test counts on English.
- **The options form of the display has two notices** once the list of thresholds is empty: ours, and "No items" of the list. Find ours by its text.
- **The app's tooltip is one shared element with one timer** (`app/src/directives/tooltip.ts:29-50`). A mouse which arrives while the page is still settling gets none; `expectTooltip` in the spec moves the mouse away and back until the tooltip shows.
- **A collection which points at `sandbox_meter`** stops the spec from dropping it. `sandbox_meter_owner` is dropped first; a collection made by hand to try a template has to be deleted by hand.
- **Playwright's snapshot of the accessibility tree does not print `aria-valuetext`.** The spec reads the attributes.
- **A choice of a dropdown found by a part of its text can be another one:** "Value" is also in "Value / Maximum", and the last match is the wrong one. The newer tests ask for the exact text.
- **The app's form does not store a value which equals what the input shows as its default.** A dropdown of the display's form which is set to the format it takes over stores nothing.
- **A column of the default width has no room for "$4,200" beside the bar.** The table of `sandbox_meter_units` gives every column a width.
- **A box can start between two pixels.** The bar of the display stands on the line of its text, so its upper edge may be at half a pixel; the test of forced colours reads the first whole row of pixels inside it.
- **Forced colours and print are emulated per page** (`page.emulateMedia({ forcedColors: 'active' })`, `{ media: 'print' }`), and Chromium's emulation has colours of its own (a dark blue `Highlight` on white, a turquoise one on black). A test compares what it reads with the colour of the page beside it, not with a colour it expects.

## Known gaps

- Only Directus 11.17.4 has been tested. The browser tests run in Chromium only; Firefox and WebKit were looked at by hand, a touch device not at all. The form was last looked at in those two before its layout became the stacked one; the display is as it was then.
- A meter in a stock Repeater was tried with an integer, a float and a big integer field, not with a decimal one, and only with the Repeater of 11.17.4. Other places which draw the options of an interface or a display inside another form (a flow's operation, a panel) were not tried; they go through the same `system-interface-options` and `system-display-options`.
- The Step input in the dialog of a Repeater's field takes decimals also for a whole type, since the dialog does not say the type. The form of the display there cannot show what the interface has, and its two toggles (Value Text, Fade In) show a default which may not be the interface's: a toggle has no way to show "not set".
- The taller target was tried with Playwright's mouse and finger. `pointer: coarse` without touch events, as a mouse on some hybrid devices reports, was not produced.
- A finger was driven through the browser's tools. How far a real finger moves sideways before a browser decides that it scrolls differs between browsers and devices; the 6px were not tuned on one.
- **A touch which drifts sideways and then scrolls the page writes** (found by the third review; left as it is for 2.0.0, where touch is not a priority and no device was at hand to try a change of the pointer path on). The meter takes a finger for a drag once it has moved 6px along the track and further along it than across (`sideways`, `TOUCH_SLOP`); the browser decides that a gesture is a scroll later, after a longer way, and by the whole movement. In between the value follows the finger. When the browser takes over it sends `pointercancel` and the value is put back, so the text flickers (measured from 30: "82%", "83%", "30%"). On a field which its own condition closes at the written value the put-back is refused, since the field can no longer be edited, and the edit stays, on a field which is read-only by then. The fix which is meant: with a finger, draw the value during the drag and write it once, when the finger is lifted, so that a cancel has nothing to take back. No test produces the diagonal start; the finger test scrolls straight up.
- Where the numbers a field can hold lie further apart than its steps (values near 1e15 with steps of a thousandth), a key goes to the next number which exists, which is more than one step, and a Page key is not ten of them.
- **The keys at the edge of a double's precision** (found by the third review; not changed). From about fifteen significant digits between a value and its step, where two points of the grid are only a few spacings of such numbers apart, a key can skip a point or stay on one and the pointer can take the farther of two points (1e9 to 1.001e9 in steps of a millionth; a big integer near 4e15 in steps of 7). In a range of more than `Number.MAX_SAFE_INTEGER` steps, which has no grid, the arrow and Page keys do nothing: a step is less than the twelve digits which are kept. Neither has a test: the reviewer's 120,000 presses on grids a field is likely to have (spans up to 1e10, steps from a thousandth) found nothing.
- Pieces which grow: the round outer end of a row of segments is squashed with its segment, and stretched with it where the segment is large under the pointer (only a large pill has its corners corrected). What lies over a piece which fades in is not eased in when the piece starts to, only while it goes on. Both were looked at in Chromium only.
- While the pointer drags the value, a piece can be at its full size, or fully faded in, a moment before the value fills it, and with steps of more than half a piece the value can fill a piece before the pointer is there, which is a jump in size. Both come from the fill staying on the steps while the sizes follow the pointer.
- The reach of thin bars is counted in half pieces, so it is about 15px and not exactly: between 12px and 20px of the track.
- The editing was tried in Chromium only, with a mouse and a finger which Playwright moves. A pen and a real touch screen were not tried. The pointer lock is tested in the full Chromium without a window; the owner tried it with a real mouse, where it worked.
- Under the pointer lock `movementX` was only seen at a device pixel ratio of 1.
- Escape ending a pointer lock in the browser's own way was not produced: Playwright's Escape reaches the page as a key. The test ends the lock from the page instead, which the meter cannot tell from it.
- `nonEditable` and `loading` were not seen on their own in a browser, and a user who may only read, and a batch edit, were not tried again since the meter can be edited. All of them reach the meter as `disabled` or as one of those two.
- A big integer beyond 2^53 is written as the nearest number which can be held, as the stock Slider does.
- Not tested with a screen reader. The role, the names and the value attributes were checked through the DOM and the accessibility tree which Playwright reads.
- Not tried next to another extension which registers an interface or a display with the id `meter`.
- `loading` was not seen on its own: the form covers the field with its own placeholder then, and the component does not declare the prop. A content version compared with the main item was not tried; the comparison of two revisions was.
- A form inside the translations interface with a right-to-left language was not tried. The meter there runs in the direction of the page, by decision.
- A database which returns `decimal` and `bigInteger` values as text was not tried: SQLite returns numbers. The unit tests and a field with limits stored as text cover the reading of such text.
- The app at the width of a phone was measured, not seen: at 390px its navigation covers the form in a fresh session.
- The raw value editor and **Clear Value**, the comparison of revisions, a user who may only read, a batch edit, the Arabic and the Hebrew user and the other two browsers were tried by hand only, and in the light theme only.
- Not tried with a custom theme.
- Forced colours were tried with Chromium's emulation only, in the light and the dark scheme: not with a contrast theme of Windows, not in Firefox or WebKit, and not with a screen magnifier. With the colours of the emulation the meter was looked at in the form, at rest, with the focus, under the pointer and without a value, and in the tables. Whether `Highlight` and `CanvasText` are far enough apart in every contrast theme for the thin bars of the display, which have no room for an outline, is not known.
- Print: the computed `print-color-adjust` is read in a page which emulates the print medium. No page was printed or saved as a PDF, and the app's own print layout was not looked at.
- The prefix and the suffix stand where they are typed in every language and direction: there is no rule which puts a unit before or behind the number for the language of the user, and they are inside the text which is marked as running from the left. A suffix in a right-to-left script was not tried. A translation string as a prefix or suffix cannot be given a space of its own: the key is the whole option, so the space has to be in the translation.
- The step of a field which sets none goes by the type and the range alone. The scale of a `decimal` column is not looked at: a column with one decimal and a range of 1 is set in hundredths, which the database then rounds, so the item can hold another value than the meter wrote. A step in the options is the way out. Below a range of 1e-13 such a field has fewer than a hundred steps, and below 1e-15 its two ends.
- The input method `none` is the interface's alone. The field stays one which can be edited: the raw value editor and **Clear Value** change it, and a batch edit can. The display is not edited anyway.
- The pieces and the colourings were looked at in Chromium only, and not in a card, in a display template or at the three row heights of the table. The row of pieces is one inline piece where the bar is. `color-mix()` and `:dir()` need a browser of 2023 or later; in an older one a faded colour falls back to the plain track or the primary colour, and a gradient does not turn in a right-to-left page.
- The pieces are counted in pixels of 16 to the rem, and drawn in rem. With another root font size the two would drift apart; the app does not change it.
- A change of the device pixel ratio while a page is open (a zoom, a window moved to another screen) is followed by `useRatio`, but no test changes the ratio of a live page: the browser tests start a browser at each of 1, 1.5 and 2, and a unit test goes through the sizes at 0.9, 1.1, 1.25 and 1.75, which the reviewer also looked at in a browser.
- How many bars fit depends on the ratio, so it changes with a zoom of the page: a range of a hundred in half of the form draws 57 bars at 100%, 47 at 110% and 53 at 125%, and the display 24, 16 and 18. With it the look of a table changes, and so can the input method: `automatic` is `piece` only where every bar is one step, as fifty bars are for 0 to 50 at 100%, and no longer at 110%, where 47 fit. The other shapes do not depend on the ratio.
- No browser test reaches the cap of 200 pieces, which takes bars in a field of twelve hundred pixels. The unit tests pin it.
- The geometry of the pieces (`pieceGeometry`) is unit-tested but not compared with the page by a test of its own: the browser tests measure the same gaps, sizes and edges piece by piece.
- A width of half a pixel more or less at the moment the count would change was not tried; the count is taken from the observer's size of the border box.
- A few packed dots in a wide field are a short row at the start, with the value text at the far end of the line under them. `spread` is there for that.
- The gaps of spread dots are not all alike on a screen: they share what the dots leave of the width, which rarely divides, so some are one device pixel wider than others (measured: 4 and 5 device pixels for 21 dots in 342px at a ratio of 1, 6 and 7 at 1.5, all 9 at 2; 4 and 5, 6 and 7, 8 and 9 for 44 dots in 713px). Gaps of whole pixels would move the last dot off the end edge, which is what spread means; not changed.
- The pieces up to the pointer are large only where the pieces are filled by the pointer (`piece`, by choice or because every piece is one step), as the tint was before them. Thin bars for 0 to 100 take the value under the pointer by default, and show none of it unless `input` is set to `piece`. The sizes were chosen and looked at in Chromium, in the light and the dark theme, with a mouse which Playwright moves. A large piece reaches up to 3px outside the track: under a caption of several lines, where the track is at the top edge of the area, that is 3px into the gap under the field's label, which nothing cuts off in the item form or in the drawer of a Repeater's row (tested there), and was not tried inside other containers.
- With pieces a value just above the minimum fills nothing, and one just under the maximum everything: only the text tells them from the ends. That is the rounding rule. Without a value, many thin bars are a lattice of dashes rather than outlines.
- A gradient is blended in sRGB by the browser, from stop to stop. In pieces it ignores the gaps: each piece shows an equal part of the scale.
- The dashed outline of a field without a value and the app's placeholder are in subdued colours, about 2 to 1 against the page in the default light theme. Neither is the only carrier of anything: the dash beside the outline is in the text colour.
- A caption of the display cannot be emptied where the interface has one: it is taken over again. A colour or a list of thresholds which was set or emptied in the display does not follow the interface again; only removing the key from the stored options does that, and the options form has no control for it.
- The order of the two pairs of limits follows what the stock Slider of 11.17.4 does with a field which holds both. Another version of Directus may differ; the browser test which reads the Slider's own limits would then fail.
- A text which does not fit is left out without a mark. In the display the tooltip has it; in the form only assistive technology and the raw value of the field do, and the line it would stand on stays empty. In the form that takes a field narrower than the text itself. A column of the default width has room for "100%" and "7 / 12" and not for "35 / 60".
- In a display template the text of the display is one piece: where it does not fit the line it is replaced by the template's ellipsis, in the smallest cards together with the bar.
- The height of the display's text box is `1lh`. The fallback for a browser without that unit, the line height of a table cell, was not tried in such a browser.
- The fraction as plain text (the display's handler) carries no direction mark, so in a right-to-left page the app may lay "7 / 12" out as "12 / 7" where it prints that string.
- "Value Text", "Thresholds", "Value / Maximum", the notes of the options, the notice of the display's options form and the fallback name "Meter" are English only.
