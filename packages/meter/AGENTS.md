# directus-extension-meter

A Directus 11 bundle extension, published on npm as `directus-extension-meter`. It adds the **Meter** interface (`meter`) and the **Meter** display (`meter`) for `integer`, `bigInteger`, `float` and `decimal` fields which hold a number that something else keeps up to date. The interface draws the number as a bar which is filled as far as the value has come between a minimum and a maximum, with the value as text beside it and a caption under it; the display draws a short bar of a fixed length and the text in layouts. In both the track can instead be a row of pills, segments, bars or dots, each filled or not, as many as the width allows, and the colours of the thresholds can belong to places on the scale instead of to the current value. In a field which can be edited the interface is also the control: the pointer and the keys set the value. In a read-only field it is a reading and nothing else, which is what it was made for: the stock Slider is a control which greys out there, and the stock displays show a number without its range.

The rules which hold for every extension of this repository (independence, bundle hygiene, code style, releasing, the sandbox) are in the root `AGENTS.md`. This file only holds what is specific to this package; `CLAUDE.md` imports it.

## Commands

Run these in this folder, after `npm install` in the repository root:

```bash
npm run dev        # watch build, unminified
npm run check      # vue-tsc, plus tsc over the tests (tsconfig.test.json)
npm test           # vitest
npm run build      # dist/app.js + dist/api.js
npm run validate   # directus-extension validate
```

`prepublishOnly` runs check, test, build and validate.

## How it works

- **A bundle with an app side only.** The manifest has the two entries and no hook, endpoint or operation. The SDK still writes `dist/api.js`, three empty lists, because a bundle has both paths. The entry names differ (`meter`, `meter-inline`), as a bundle needs; the ids are the same, since Directus registers interfaces and displays apart. The stock id `meter` is a panel of Insights, a third registry.
- **The display never writes. The interface writes only where its field can be edited.** `editable` in `interface.vue` is `canEdit(props)`, which is `!disabled && !nonEditable && !loading`: the three props by which the form says that a field is read-only (by its settings, by a condition, by the permissions of the user, in a batch edit), shown where nothing is edited (the comparison of revisions) or still loading.
  - **Not editable is the meter of 1.0.1,** element for element: the role `meter`, the classes and attributes it had, no `tabindex`, no handle, no listener (the template binds `v-on` to an empty object), no cursor, no `touch-action`. It is not dimmed: a field which a flow maintains is normally read-only, and dimming it would dim nearly every meter.
  - **Three things stand between a field which cannot be edited and an emit,** on purpose: no listener is bound; every handler returns at once unless `editable`; and `write`, through which every value goes, checks it again. `finish`, which puts a value back on Escape, checks it too. Take none of them out because another is there.
  - **The form is a fourth, and hides mistakes.** The item form of 11.17.4 drops what a disabled field hands it (seen: with every guard of the meter taken out, a click on a read-only meter still changed nothing in the page). So a test which only looks at the value proves nothing about the meter. The browser tests ask the browser which events the element listens to (`DOMDebugger.getEventListeners` through a CDP session, `listened()` in the spec): none for a meter which cannot be edited, six for one which can.
  - **`nonEditable` and `loading` were not seen on their own.** In the comparison of revisions the app sets `nonEditable` together with `disabled`, and while a form loads it covers the field. The rule for all three is a pure function with unit tests of every combination.
  - **A field which stops being editable during a drag** lets go of the pointer and of the lock at once (`watch(editable)`). A condition on the field's own value does that: the field `closing` of the spec is read-only from 50, and a drag across 50 closes it with the button held.
  - **This changed what existing fields do.** Before, no meter wrote. A field whose meter must stay a reading has to be read-only in its settings; the README and the changelog say so.
- **What is written is made in one place** (`snapValue`), and `write` takes nothing else: a finite number, on the grid of steps counted from the minimum, within the range, or the maximum.
  - **The grid starts at `min`.** `min + n * step`, for a whole `n`. A range from 1 with steps of 2 has 1, 3, 5.
  - **The maximum can always be written,** also where the grid misses it: steps of 3 from 0 to 10 are 0, 3, 6, 9 and 10. Otherwise a meter could never be full. Between the last point of the grid and the maximum the nearer of the two wins.
  - **No dust.** The result is rounded to as many decimals as the step, the minimum and the maximum have between them (`decimalsOf`, from how the numbers are written out), so `0.1 * 3` is written `0.3`. With more than 15 decimals nothing is rounded.
  - **Whole types.** `integer` and `bigInteger` (`type`, which the form hands every interface) get a whole step of at least 1 (`readEditing`), a grid which starts at the first whole number of the range, and a whole number. A range without a whole number in it has nothing to write (`null`), and nothing is written.
  - **One range for everything which edits** (`writableRange`): the range as it is drawn, and for a whole type `ceil(min)` to `floor(max)`. The grid of `snapValue` starts at its minimum. `automatic` is `segment` only where it is the drawn range itself. A key counts from its nearer end for a value from outside, Home and End are its ends, and a piece of a Page key is a piece of it. A slider says it as `aria-valuemin` and `aria-valuemax`. The drawing does not use it: the fill is still against `min` and `max` as stored, and a meter which cannot be edited says those. Before there was this one range, an integer field from 0.5 to 5.5 in five pills filled by the piece wrote n + 1 for a press on piece n.
  - **Steps which make no grid.** A step larger than the range leaves the two ends of the range, and the nearer is written (a key takes the end it points to). Where the range holds more than `MAX_STEPS` steps, a thousand million, the grid cannot be counted with any meaning (the slack which makes 0.3 three steps of 0.1 is then as large as a step): the value within the range is written, rounded to `FREE_DIGITS`, twelve, digits which count.
  - **A number for every type.** The stock Slider of 11.17.4 sends a JSON number for `integer`, `bigInteger`, `float` and `decimal` alike (seen in the body of the request which saves an item: `6`, `6`, `4.5`, `4.5`). The stock Input sends a number too, but for `bigInteger` the text `"7"`. The meter does as the Slider does. A big integer beyond 2^53 is therefore not exact, as in the Slider.
  - **Three roundings.** The pointer goes to the nearest value, with the upper one half way. A key goes to the next value below or above where it lands (`'down'`, `'up'`), so that a step up from 3.7 on a grid of 1 is 4 and not 5.
  - **Only a change is written:** `write` asks `changes(held, next)`, which compares with the number the field holds (`numberOf`, so the text `"5"` of a decimal is 5). The form would drop an edit which equals what is stored, so this too is pinned by unit tests and not seen in the page. The one thing which is emitted without going through `snapValue` is what Escape puts back: exactly what the field held at the press, be it `null` or a value from outside the range.
  - **The step is `step`,** and `stepInterval`, the key of the stock Slider, while `step` is not set (missing, `null` or blank), as `minValue` and `maxValue` stand in for the limits. A `step` which is set and is no number above zero is 1; it does not fall through to the Slider's.
- **The three input methods, and why `automatic` chooses as it does** (`inputMethod`).
  - **`contiguous`:** the share of the track at the pointer, as a value, snapped. For packed dots the track is the row of dots (`frame().length`), not the width of the field, or a click on the fifth of ten dots would give a quarter.
  - **`segment`:** `filledAt` counts the pieces whose start the pointer has reached, in `pieceGeometry`, the same data the pieces are counted and laid out by; what is written is `segmentValue`: of the values which can be written and which draw exactly that many pieces, the one nearest to that share of the range, so that the piece which was pressed is the last one filled; where no value draws that many, as with more pieces than steps, the nearest value. Where a piece is a step that is the share itself. A gap belongs to the piece before it, before the first piece is the minimum, beyond the last is the maximum. On one bar there are no pieces, and it is `contiguous`.
  - **`relative`:** `relativeMove` adds `movement / length * range * sensitivity` (a tenth of it with Shift) to a value which is kept unsnapped for the length of the drag (`drag.raw`), within the range, and what is written is that value snapped. Kept unsnapped, forty movements of a quarter step are ten steps; kept within the range, the first movement back from an end counts.
  - **`automatic` is `segment` exactly where `count * step` is the range and the limits themselves can be written,** which is where a piece stands for one step and a click on the third piece can only mean three steps. Where a piece is several steps, as ten pieces for 0 to 100 at a step of 1, filling by the piece could reach only every tenth value of the grid, so the pointer sets the value under it instead and all hundred can be reached. Where a piece is less than a step the pieces mean nothing as targets either. It is never `relative`: that method changes nothing on a press, which nobody expects of a meter they did not set up that way.
- **Pointer events, one press at a time.** `pointerdown` of the primary button of the primary pointer starts a drag and captures the pointer, so the drag goes on outside the field; `pointerup` ends it, `pointercancel` (a finger which starts to scroll) ends it and puts the value back. `touch-action: pan-y` leaves vertical scrolling to the page. `lostpointercapture` is not listened to: a pointer lock takes the capture away when it is granted. A press which never saw its release is ended by the next press, and by a mouse which moves with no button held.
- **Pointer lock, and its fall-back.** The relative method asks for the lock on the press (`requestPointerLock`, not for a finger). While `document.pointerLockElement` is the track, a movement is `movementX`; otherwise it is the difference of `clientX`, with the pointer captured. That question is asked at every movement, not remembered: the first movement under a lock arrives before `pointerlockchange` does (seen: a fifth of a drag was lost that way). The lock is given back on release. A lock which ends while the button is held was ended by the browser, as on Escape, and counts as Escape; one which arrives after the release is given back at once. A refusal (the promise rejects, or the method throws, or is missing) changes nothing: the drag is already working.
  - **In the sandbox's browser** (Playwright's headless shell of Chromium) the lock is refused: `WrongDocumentError`. The same Chromium started as the full browser (`channel: 'chromium'`), still without a window, grants it. The browser test of the relative method runs its steps in both.
- **Keys** (`keyValue`): Right and Up one step up, Left and Down one down, Left and Right swapped where the computed direction of the track is `rtl`; Page Up and Page Down ten steps (`PAGE_STEPS`), or one piece where that is more; Home and End the two ends of what can be written. A value from outside the range is first brought to the nearer of those ends, and the key counts from there: 150 of a hundred and Left is 99, and 15 on a whole type from 0 to 10.5 is 9. A key of the meter's is `preventDefault`ed whether or not it changes anything, so the page does not scroll; a key with Ctrl, Alt or Meta is left alone. Escape is the meter's only during a drag, and is then stopped from going further.
- **What shows that it can be edited takes no room.** The cursor (`pointer`, `ew-resize` for the relative method). A handle on the one bar: a dot of 0.5rem inside the track at the end of the fill, clamped so that it is inside at both ends of the range, visible under the pointer, under the keyboard's focus and during a drag, shown and hidden without a transition. A veil over the pieces which the pointer would fill (`mt-hint`), while it rests over a meter whose pieces are filled by it: none during a drag, where the fill itself follows the pointer, and at once again at the release, worked out from where the pointer is then (`rest`), without waiting for it to move. A focus ring as an outline. The app has its own ring for every focused `div`, drawn inside the element with square corners (`div:not([contenteditable=true]):focus-visible` in its global styles, which also sets `border-radius: 0`); the meter's two rules are written with one class more than they need to come before it, and give the track its round ends back.
- **Everything goes through `readOptions` and `readingOf`.** The components hold no arithmetic. `readOptions(own, inherited)` takes the options as the schema stores them, which is untrusted, and returns an `Options` in which every key has a usable value. `readingOf(value, options, locale)` returns what is drawn: whether there is a value, the fraction filled, the value kept within the range for `aria-valuenow`, the text and the colour. The interface calls `readOptions(props)`, the display `readOptions(props, interfaceOptions)`, the handler the same with the context it is handed, so the three cannot disagree.
- **The fall-back is key by key, and there are two kinds of key.** For the limits, the caption, `indicator` and the format, the first source which holds something usable wins: the entry's own options, then the options of the field's interface. Usable is a number or the text of one for a limit, non-blank text for the caption, a boolean for `indicator`, one of the three formats. So a cleared option (`null`), a broken one and a missing one all fall through, and `indicator: false` of the display wins over `true` of the interface. For `color` and `thresholds` only a missing key falls back: a key which is there counts whatever it holds, so an emptied colour is the default colour and an emptied list no thresholds. The reason is the options form. It shows the interface's colour and list as the default of its inputs only while the key is missing; once the user empties one, `null` is stored and the form shows an empty input, so the layouts must draw none. For limits and caption the form shows what is taken over as a placeholder, which shows whenever the input is empty, so there an emptied option can go on falling back. The display tells the two apart because an option which was never set arrives as `undefined` and an emptied one as `null`.
- **Four keys for two limits.** A limit is `min` or `max`, which are also the keys of the stock Input (`app/src/interfaces/input/index.ts:147, 156`), or else `minValue` or `maxValue`, the keys of the stock Slider (`app/src/interfaces/slider/index.ts:16, 25`). Both entries read both pairs from every source, `min` and `max` first. That is what makes the display work on a Slider field, and what keeps the range of a field which is moved from the Slider to the Meter: the app keeps a field's options when its interface changes, so such a field holds `minValue` and `maxValue` and no `min` or `max`. The interface therefore declares `minValue` and `maxValue` as props although its form has no input for them. Were only the display to read them, form and table of such a field would show two different ranges.
- **A field which holds both pairs is read by `min` and `max`, on a Slider field too.** One would expect the Slider's own pair to count there. It does not: the stock Slider of 11.17.4 does not declare `min` and `max`, so they fall through to the component inside it, whose range they are, and override the two it was given (`app/src/interfaces/slider/slider.vue:38-49`). A Slider field with `{ min: 0, max: 10, minValue: 1, maxValue: 5 }` runs from 0 to 10, with eleven ticks, and lets the user choose 10 (seen). The display has to show the range the form shows, so the order is the same for every interface. The browser test reads the limits from the Slider's own `input` and compares the display with them; should a later Directus make the Slider keep to its own pair, that test fails, and the order for a Slider field has to turn around (the display is handed the id of the field's interface as `interface`, the handler as `context.field.meta.interface`).
- **The range is put in order once.** `readOptions` returns `min` as the smaller and `max` as the larger of the two, after the fall-back and the defaults. Everything after it can rely on `min <= max`. With `min === max` the fraction is 0 below that number and 1 from it upward, and the percentage 0 and 100.
- **The bar is clipped, the text is not.** `fractionOf` stays within 0 and 1; `percentOf` does not, so 150 of 100 is "150%". A value strictly inside the range is never 0 or 100 percent: it is rounded and then held between 1 and 99.
- **Nothing which is not finite reaches the page.** `numberOf` takes a finite number, a big integer or the text of a number as the API writes it, and nothing else: not `Infinity`, not hexadecimal, not blank text. `shareOf` halves the numbers where their difference would overflow. A fraction is always finite, and the text never holds `NaN`; a unit test runs extreme values against extreme limits for exactly that. The app's error boundary around a display does not contain an error thrown while the browser is handed a display's output: one bad cell can blank a layout.
- **Numbers are written by `Intl.NumberFormat` in the language of the user.** `useLanguage` reads `$i18n.locale` from the app's global properties, which is tracked, and falls back to `lang` of the root element (`app/src/lang/set-language.ts:28-30`); the handler has no component and reads the root element. A tag which the browser does not take falls back to the browser's language instead of throwing. Formatters are kept in a map, since a table makes one text per row. Value and maximum have at most two decimals; a number below 1 keeps two digits which count; from 1e15 upward and below 1e-6 an exponent is used, because the digits of a larger number are not all true and a smaller one would be a row of zeros.
- **The text of a number is marked as running from the left** (`dir="ltr"`) in both components. A number has no direction of its own: in a right-to-left page "-20%" would be laid out as "20%-" and "7 / 12" as "12 / 7". The number formatting of a right-to-left language puts the marks it needs into the text itself, so Arabic still reads from the right.
- **`direction` is not used.** The form hands every interface the direction of the text typed into the field: the form of an item that of the user (`app/src/modules/content/routes/item.vue:888`), a form inside the translations interface that of its language (`app/src/interfaces/translations/translation-form.vue:213`). The meter holds no such text, and like the stock Slider it runs in the direction of the page, which the logical properties of its styles follow without any code.
- **The interface is one area, as high as a stock input.** `.meter` is a column with a minimum height of `--theme--form--field--input--height` (54px in the default theme) which centres what is in it: the track, across the whole width, and 0.25rem under it one line with the caption at the start and the value text at the end. Nothing is drawn outside the area, so the note which the form prints under a field is where it is under an input, and the field takes the room of an input. A caption which wraps makes the area grow. With no caption the text is alone at the end of the line; with the text off the caption is alone; with neither there is no line and the track is in the middle. No border and no background. The track is 0.75rem high with rounded ends, in the colour token of the stock Slider's line; the fill is a block at its start, sized along the inline axis.
- **The line gives the caption what the text leaves.** It is a flex container: the text keeps its width (`flex: none`) at the end (`margin-inline-start: auto`), the caption takes the rest and wraps, so the text stands at the end of the caption's first line. The caption asks for 4rem before it gives way (`flex: 1 1 4rem`); where the field has no room for that and the text together, the line wraps and the text goes under the caption, still at the end and still whole.
- **Five ways to draw the track, under the key `visualization`.** `contiguous` is the one bar and the default. `pills`, `segments`, `bars` and `dots` cut the track into pieces which are each filled or not. `readLook(own, inherited)` reads the word, the number of pieces which is wanted (`subdivisions`), the layout of the dots (`dotsLayout`) and the two colourings (`activeColoring`, `inactiveColoring`), apart from `readOptions`, with the fall-back of the limits: the first usable value among the entry's own options and the interface's, so a missing, an emptied (`null`) and a broken one all fall through. Any other word is the default. `Options`, `Reading`, `readOptions` and `readingOf` know nothing of any of it.
- **The key is `visualization` and not `style`.** Options arrive as props, and Vue binds an attribute called `style` to the element instead of handing it over.
- **How many pieces: wanted, capped by what fits** (`pieceCount`, which is `drawnCount(wantedCount, fitCount)`).
  - **Wanted** (`wantedCount`): `subdivisions` when it is a whole number or the text of one, 2 where it is less, with no largest. Otherwise `max - min`, after the fall-back and the ordering of the range, when that is a whole number of at least 2. Otherwise nothing in particular (`null`).
  - **Fit** (`fitCount`): `floor((width + gap) / (piece + gap))` with the smallest piece and the gap of the visualization in its place, from `PIECE_SIZES`: in the form pills 20 and 4, segments 14 and 3, bars 3 and 2, dots 12 and 6; in the display pills 8 and 2, segments 6 and 2, bars 2 and 1, dots 6 and 1.5. These are pixels at 16px to the rem, and the styles of the two components draw the same gaps and dots in rem: change one and the other together.
  - **Drawn** (`drawnCount`): what is wanted where it fits; else the largest number of at least 2 which fits and divides it (100 with room for 29 is 25, 12 with room for 7 is 6); else, for a prime and for nothing wanted, as many as fit; and 0 where fewer than two fit, which makes the meter one bar.
  - **One cap for the whole package,** `MAX_PIECES`, 200, on what fits and so on what is drawn: every piece is an element.
- **The look depends on the width, and that is decided.** The fixed limit of ten pieces which an earlier draft had is gone. The same field has ten pills in half of the form, 25 across it and five in a table. Whoever wants the same everywhere sets a small number.
- **The form measures, the display does not.**
  - **The interface** has a `ResizeObserver` on the element on the line of the track, which is the track of the one bar or the row of pieces: one element in both cases, so the reference stays. The form gives it its width (it is a stretched item of the column), never what is in it, so the count cannot feed back into what is measured. It is measured once in `onMounted`, so the first frame is right, and the observer is disconnected before unmount. The width is in a `shallowRef` which only the computed `count` reads; a computed value which comes to the same number does not wake what depends on it, so the template is rendered again only when the count changes. Do not read the width in the template or in anything which draws: the gradient is laid out without it for that reason.
  - **A field without a width,** in a tab or group which is not shown, fits none: it draws the empty one bar, which keeps the height, and is measured again when it is shown.
  - **The display** hands `DISPLAY_WIDTH`, 72, to the same function. Its bar has that length in every row, so 7 pills, 9 segments, 24 bars or 9 dots fit, always.
- **How many are filled** (`filledCount`): `Math.round(fraction * count)` with the fraction of the one bar, which is already within 0 and 1. The first that many are filled, completely; no piece is ever filled in part, and nothing marks a value just above the minimum as the dot of the one bar does. Only the drawing is rounded: the text, the tooltip, `aria-valuenow` and `aria-valuetext` are those of the real value.
- **Where the pieces are is plain data** (`pieceGeometry`): the start and the end of every piece in pixels from the start side, for a shape, a place, a count, a width and a layout of dots. Nothing draws from it today: the styles lay the pieces out by the same rules (flex with a gap, or `space-between`). It is there, unit-tested, for whatever has to find the piece under a point.
- **The pieces in the form.** The row (`mt-strip`) stands where the track stands, at its height, and carries the role and the values as the track does; the line under it and the area around it are untouched. It is a flex container, so the first piece of the document is at the start side in either direction. Pills, segments and bars share the width equally. Pills (`mt-pills`) are 0.25rem apart and round at both ends. Segments (`mt-segments`) are 0.1875rem apart and square, but for the start of the first and the end of the last, by logical corner properties, so the row reads as one rounded bar which is cut. Bars (`mt-bars`) are 0.125rem apart and square. Dots (`mt-dots`) are circles as high as the track which do not stretch: 0.375rem apart from the start, or with `mt-spread` from edge to edge by `space-between`. Without a value every piece is a dashed outline like the track's (`mt-empty`).
- **The pieces in the display.** The row (`md-strip`) is an inline flex container in the place of the bar, one unbreakable piece like it and as long as it, and the role stays on the root. Pills and segments are 0.125rem apart, bars 0.0625rem, with the corners as in the form at the display's height. Dots are 0.375rem across, smaller than the bar is high so that nine fit. Packed (`md-packed`) they are 0.09375rem apart and the row is as long as its dots; the root is told that length (`--md-bar`, set inline) because the room of the text is worked out from it. Spread (`md-spread`) they take the length of the bar.
- **Colouring: a colour for a value, or a colour for a place** (`drawingOf`, which both components draw from).
  - **The stops** (`scaleStops`): the colour of a meter at its minimum, at 0, and every threshold above the minimum at its share of the range, in rising order. A threshold beyond the maximum is beyond 1 and stays in the list: CSS takes a stop outside the box. Fewer than two stops means one colour, and every colouring is drawn as `value` then.
  - **`value`:** the colour of the reading, as before, as an inline `background-color`.
  - **`blend`:** one colour as well, for the fill and for every filled piece: the colour the gradient has at the place of the value (`blendAt`: the two stops around the place and the share between them; `blendCss`: `color-mix(in srgb, <from> <100 - share>%, <to>)`, mixed by the browser because a stop may be a theme variable). The place is that of the stored value, which `drawingOf` is handed as its fifth argument, so a value beyond the range blends on towards a threshold beyond it. On a threshold and from the last one on it is that threshold's colour. As the colouring of what is not filled it is the same colour, faded.
  - **`steps`:** a piece has the colour of the value it reaches when it is filled completely (`valueAtPiece`, which multiplies before it divides so that the 57th of a hundred reaches 57). The one bar has a gradient with two stops at every threshold, so the colour changes at once.
  - **`gradient`:** the stops as a CSS gradient across the whole track, of which every surface shows its own part. The surface has the class `mt-paint` (`md-paint`): its background is `--mt-n` times as wide as itself and placed at `--mt-at`, from 0 for the first part to 1 for the last, which as a percentage of `background-position` moves the image by that share of what it is wider than the box. A piece is one of `--mt-n` equal parts, with the gaps between pieces not counted, so nothing depends on a measured width. The fill of the one bar is not sized by `--mt-n`: its image is as wide as the track itself, `100cqi`, with the track made a size container where its fill is painted so (`mt-scaled`); in the display it is the bar's 4.5rem. The blend is never squeezed into the fill, and no stop can move.
  - **A place keeps its colour to the pixel while the value changes.** The fill of the one bar used to have an image `1 / fraction` times its own width, which is the width of the track only in exact arithmetic: at each value it came out a fraction of a pixel wider or narrower, and the place where one colour ends jumped between two pixels during a drag (seen: 136 and 137 in a track of 342px). Never size a painted surface by something which changes with the value. `--mt-n` is still set on the fill, for a browser which does not know the unit and drops the declaration. Pieces never had this: their sizes do not depend on the value.
  - **What is not filled** (`inactiveColoring`): `plain` is the track of the styles. Otherwise one of the three ways, `automatic` being the way of what is filled, and faded.
  - **Faded** (`fadedColor`, `FADE`): `color-mix(in srgb, <colour> 30%, <the track's colour>)`, seven parts of the track in ten, in every theme. The browser mixes, because a colour may be a theme variable; script never computes a colour. Chosen by eye: at 30% the hue still shows on the light and on the dark track, and the filled part stays clearly stronger.
  - **The stops reach CSS in two custom properties on the root,** `--mt-stops` and `--mt-weak-stops` (`--md-…` in the display), and a faded surface has a rule of its own which reads the second (`mt-weak`). It must not set `--mt-stops` for itself: the fill is inside the track and would inherit the faded stops (seen).
  - **A gradient has no logical direction.** `to right` is mirrored for a right-to-left page by `:dir(rtl)` rules, which also count the place from the right. The app writes `dir` on the root element.
  - **No value has no colours:** `drawingOf` returns nothing to paint, and the dashed look stays.
  - **Every colour in a stop list went through `isColor`,** as it is or inside the one `color-mix`.
- **A field which sets none of the new options is drawn as in 1.0.1,** element for element: no `style` on the root or the track, the classes `mt-track` and `mt-fill` alone, the colour of the reading inline on the fill. A browser test reads those attributes.
- **The options form asks only for what applies.** `optionFields` is handed the options of the entry as the form holds them, and leaves the `subdivisions` input out while the visualization comes to `contiguous`, and the `dotsLayout` dropdown unless it comes to `dots`. The app calls the function again whenever an option in the drawer changes (seen). A value which was stored stays stored while its input is hidden, and is ignored. The placeholder of the number is the app's own "Automatic" (`$t:automatic`, which the form translates in a placeholder too; seen), or the interface's number in the form of the display.
- **The dropdowns of the display can be emptied.** `visualization`, `dotsLayout`, `activeColoring` and `inactiveColoring` have `allowNone` in the form of the display, which adds the app's "Deselect" to the list and stores `null` (seen). `null` falls back like a missing key, and the dropdown then shows what it comes to as its placeholder. In the form of the interface they cannot be emptied: there is nothing to go back to.
- **A fill is never narrower than the track is high.** The smallest value above the minimum shows as a dot, not as a sliver of a rounded corner. At exactly the minimum, and below it, there is no fill element at all.
- **Tracks are always as wide as their field,** whatever the text beside the caption says, so tracks one above the other end at the same place.
- **The text of a number is whole, or it is not shown.** Never a part of it: a part reads as another number, whether it is the first digits ("5" for 50%, "999,…" for 999,999,999,999,999), the last ones or, of a fraction in Arabic digits, the maximum alone, and an ellipsis does not mend that. So nothing cuts a number, in any script or direction, and there is no code which knows about either. Both components let the text wrap to a second line which is cut off.
  - **In the interface** the text has a box of its own on the line under the track, as in the display: a flex container which may wrap, one line high (1.25rem, the line height of that line), no wider than the field (`max-inline-size: 100%`), with `overflow: hidden`. Its first item is a space without a width (`::before`, U+200B), which holds the first line; the number is the second, and wraps away when the field is narrower than the number. The box keeps its line even then, so a field which is that narrow has an empty line where the text would be.
  - **In the display** the bar cannot be the thing which holds the first line, since bar and text have to stay two pieces of a template's line. The text has a box of its own: an inline flex container which may wrap, one line high (`1lh`, with `1.25rem`, the line of a table cell, for a browser without the unit), with the room the bar and the gap leave (`100% - 5rem`), and `overflow: hidden`. Its first item is a space without a width (`::before`, U+200B), which holds the first line; the number is the second, and wraps away when it does not fit.
  - **That box is a flex container and not an inline block for the sake of the line.** An inline block which cuts its content sits on the line by its lower edge and not by the line of its text, which makes the line taller and the number stand too high beside other text. A flex container sits by the first line of its first item, here the space. Chromium, Firefox and WebKit agree on that (measured).
  - **What is left out can still be had.** The display's tooltip always has the value text (`tooltipOf`), after the caption when there is one, and `aria-valuetext` has it in both components.
- **No value has its own look.** `reading.empty` puts `mt-empty` on the root: the track loses its background and gets a thin dashed outline in `--theme--foreground-subdued`, and the text is a dash. The outline is not in the colour of the track, which is 1.2 to 1 against the page and too faint for dashes. A value which is not a number is treated as no value in the interface.
- **No transition anywhere.** The form hands every interface `null` until the item has loaded, so a transition would play on every page load, and the value only ever changes from outside.
- **The role is on the track:** `slider` with `tabindex="0"` and `aria-orientation` where the field can be edited, `meter` where it cannot, both with `aria-valuemin`, `aria-valuemax`, `aria-valuenow` (the value kept within the range) and `aria-valuetext`. A slider says the range which can be written and the value within it, and where the field has no value the least of that range, since a slider has to have a value; a meter says the range as stored, and no value where there is none, as in 1.0.1. `aria-valuetext` is the text beside the bar, whether or not it is drawn, and the app's `no_value` for a field without a value. It is named by the caption through `aria-labelledby`, else by the name of the field (`fieldData.name` in the interface, the app's store of fields in the display), else "Meter". The visible text of the interface is `aria-hidden`, so it is not read twice; in the display the text is a child of the meter, which assistive technology does not read into.
- **The display is inline, with two atomic pieces.** Its root is an inline `span`, as the stock text display is, so in a display template it is part of the line. A table cell is a flex container, which makes the root a block as wide as the cell allows; only then do its own `overflow` and `white-space` apply. The track is an `inline-block` of 4.5rem which never shrinks; as the first thing on its line it is clipped by a cell narrower than itself. The text is the box described above. In a display template each of the two is one piece which the template's ellipsis replaces when it does not fit the line. The gap between bar and text is a margin of the track, because the number has a direction of its own. A value which is not a number is plain text in the same root (`md-plain`) and is cut like any other text, with an ellipsis.
- **The display never gets `null`.** The app draws its own placeholder for it (`app/src/views/private/components/render-display.vue:25`). A value which is not a number is shown as plain text, and blank text as the app's placeholder (`value-null`).
- **The options form is one function for both entries** (`optionFields`). It is a function of the field in both, and shows what an option which is not set comes to: for the display the options of the field's interface, as the placeholders of the limits and of the caption and as the `default_value` of the other inputs; for the interface the limits a Slider left behind. A default which a form shows is not stored, which is what keeps the fall-back in place, and it is shown only while the key is missing, which is why an emptied colour or list means none (see the fall-back above). The display's form starts with a notice which says all of this in three sentences, a field of the type `alias` with `no-data`, which stores nothing. The limits are `float` so that the inputs hand over numbers; a `decimal` input would store their text (`app/src/constants.ts:171-173`).

## Invariants: do not break

1. **Stored values and option keys are public API.** The field holds a plain number, which the display never writes and the interface only as a number on its grid of steps. `input`, `step` and `sensitivity` of the interface keep their names and meanings once they are released, as do the four input methods; `stepInterval` keeps being read as the step. The ids `meter` (interface) and `meter` (display), and the option keys `min`, `max`, `label`, `indicator`, `indicatorFormat`, `visualization`, `subdivisions`, `dotsLayout`, `color`, `thresholds`, `activeColoring` and `inactiveColoring` with the keys `value` and `color` of a threshold, keep their names and meanings once they are released, as do the three formats `percent`, `value` and `fraction`, the five visualizations `contiguous`, `pills`, `segments`, `bars` and `dots`, the two layouts `packed` and `spread` and the words of the two colourings. `minValue` and `maxValue` keep being read as limits.
2. **Read loosely.** Limits and thresholds arrive as numbers or as their text, and a `decimal` or `bigInteger` value as text on some databases. Options which were stored by another interface or by hand must keep working: `min: "0"`, `max: "12.5"`, `indicator: true`. A display which has options of its own draws by them, whatever its interface has: the browser test of the fields `apart`, `muted` and `rated` pins that.
3. **The options form of the display shows what the layouts draw.** Whoever changes the fall-back of a key changes what the form shows for it, and the other way round. An option which was never set arrives as `undefined` and an emptied one as `null`; do not give a prop a default, which would hide the difference.
4. **The defaults are in the components, not in the form.** Options arrive as stored, and a default which the options form shows is not stored. `indicator` defaults to on. Do not type a prop as a boolean: Vue would turn a missing one into `false`, and the display's could then not fall back.
5. **Never throw, never hand the page a number which is not finite.** See "How it works". Keep the unit test which pins it.
6. **Nothing falls through.** `inheritAttrs: false` in both components, and no template binds `$attrs`: the form passes some twenty props and two listeners to every interface, and a layout a handful to every display.
7. **The options are untrusted.** Text reaches the page only through `v-text`. A colour reaches CSS only after `isColor`, which takes a hex colour or one `var(--theme--...)` and nothing else, so there is no room for a second declaration or a `url()`.
8. **`meter.ts` stays free of Vue, the DOM library and Directus,** and `options.ts` of everything but a type of Directus. `tsconfig.test.json` type-checks both without the DOM library.
9. **A field which cannot be edited never emits, and is the meter of 1.0.1.** No dimming for `disabled`, no pointer reaction, no tab stop, no listener, no handle. A field which can be edited never writes anything but what `snapValue` made: a finite number on the grid, within the range, whole for a whole type. No transition in either.
10. **`contiguous` with the default colouring is the meter as it was.** Whatever is added must leave its markup, its styles and its tests alone. A piece is filled or not, never in part, and what is said about the value is never the rounded one. The number of pieces comes from the width of the track's own line and from nothing which the pieces could change.
11. **A number shows whole, or not at all.** Never a part of it, in any script or direction, with or without an ellipsis: what is left would read as another number. No `text-overflow` on a number, and no box which can cut one in the middle.
12. **Bundle hygiene.**
   - The root `AGENTS.md` has the rules. There are no dependencies to bundle, and none should be added. `vue-i18n` in particular is not imported: `src/i18n.ts` reads `$t` and `$i18n` from the app.
   - `dist/app.js` is about 36.1 KB (11.7 KB gzipped; 13.7 KB in 1.0.1, 25.4 KB with the pieces and the colourings, before the editing) and `dist/api.js` 72 bytes. Report size changes.
   - **No comments in the `<style>` blocks.** The build keeps them in the bundle, so what the styles rely on is written at the end of each component's script, which is not shipped, and under "How it works" here. `grep -o '/\*' dist/app.js | wc -l` is 0 after a build.
13. **It is an app-only bundle,** so the Marketplace can install it under the default `MARKETPLACE_TRUST`. Don't add API entries casually.
14. **Directus look.** Only `--theme--*` tokens for colours: the track in `--theme--form--field--input--border-color`, as the stock Slider's line and progress bar, the fill in `--theme--primary` unless an option says otherwise, the text in `--theme--foreground`. Styles are scoped; class names other than the two roots (`meter`, `meter-display`) start with `mt-` in the interface and `md-` in the display.

## Code style

The root `AGENTS.md` has the style of the repository. In this package also:

- The unit tests cover `meter.ts` and the list of fields which `options.ts` builds. Everything in the two components, and what the app makes of the options form, has to be checked in a browser.
- The names of the options are the app's own strings where one says exactly the same (`$t:interfaces.input.minimum_value`, `$t:interfaces.input.maximum_value`, `$t:label`, `$t:format`, `$t:color`, `$t:automatic`, and `$t:percent` and `$t:value` for two of the formats). "Value Text", "Thresholds", "Value / Maximum", "Visualization", "Subdivisions", "Dots Layout", "Active Coloring" and "Inactive Coloring" with their choices and the notes have no such string and are plain English; the placeholder of the number of subdivisions is the app's `$t:automatic`. The package has no translations of its own: `src/i18n.ts` only reads the app's.
- The key of the format is `indicatorFormat`, not `format`: the stock Formatted Value display stores a boolean under `format`, and the options of a field can outlive a change of its display.

  - a read-only field: the role of a meter, the attributes and the class of 1.0.1, no tab stop, handle or cursor, and no listener for any event, where the same meter which can be edited has six; a click, a double click, a drag, keys and events sent straight to its element change nothing; Tab passes it; the same meter which can be edited has every box in the same place and the same colours; its handle is hidden until the pointer or the keyboard's focus is on it, is a dot of 8px inside the track at the end of the fill, and stays inside at both ends; a field which a condition makes read-only is a slider until the rule matches, a meter while it does, and a slider again after; only the fields which could be edited are in what is saved;

Each of these tests was shown to fail with the behaviour broken, by a throwaway change to the source which was then undone: 29 such changes for the tests as they were after two rounds of review, 9 more for those which the third round changed or added, and 46 for the tests of the pieces and the colourings: 15 for the rules of the count, 14 for the shapes in the form and in the display, and 17 for the colouring. The unit tests catch 20 of them as well. The cap of 200, the place of a threshold in a range which does not start at 0 and a tinted meter without a value are caught by the unit tests alone. For the editing, 62 more: 12 for the snapping and for whether a value is a change, 22 for the three input methods and Escape, 14 for the states which cannot be edited, 11 for the keys and 3 for the handle and a first value. The unit tests catch 28 of them. Four were caught by nothing at first: a field which is shown and not edited or which is loading being edited, every guard taken out with the listeners bound, and a value written although the field holds it. The first two cannot be produced in the app, and the form drops what the other two would do. That is why `canEdit` and `changes` are pure functions with unit tests and why the spec asks the browser for the listeners of an element; with those, all four are caught. `nonEditable`, `loading`, whether a value is a change, the rounding of a key and the Page key which is a piece are caught by the unit tests alone. After the review of the editing, 14 more for its new tests: 3 for a field which closes itself during a drag, 7 for the range which can be written and 4 for the steps which make no grid, all caught; and the test of the colours during a drag was shown to fail with the fill sized by itself as it had been. Two things no test can see in the page: the relative method keeping a wound-up value within the range in the line which a second line repeats, and the component leaving out the question whether a value is a change, which the form answers for it.

Things which are easy to trip over:

- **A click right after a page opens lands on a cover.** The app fades out an element over the whole page (`.hydrating`) for a moment after the form is there. `openEdit` in the spec waits until it is gone.
- **The app keeps a list of the keys which are down,** for its shortcuts. A `keydown` which a test sends to an element without a `keyup` stays in that list, and Ctrl+S no longer saves. `keyOn` in the spec sends both.
- **Home, End and the Page keys scroll the page** when no meter has the focus, and the scrolling goes on for a moment. The test of the read-only field sends them to the element instead, and measures the two twins in one `evaluate` each.
- **A field with an odd number of half-width fields before it starts a row at the right.** The twins of the spec have an even number before them, so they are one row.
- **The pointer lock cannot be had in the browser of the tests.** A test of its own starts the full browser for it (`playwright.chromium.launch({ channel: 'chromium' })`), signs in as the fixtures do, and is skipped with the reason where that browser cannot be started, so a runner without it shows a skipped test and not a passed one.
- **A finger can be driven.** A context with `hasTouch`, `page.touchscreen.tap` for a tap and `Input.dispatchTouchEvent` through a CDP session for a finger which moves.
- **The handle lies over the colours near the end of the fill.** A test which reads the colours of the track from a screenshot keeps 16px away from the end of the fill, or reads a place which the fill is well past.
- **The listeners of `document` can be asked for like those of an element** (`documentListens` in the spec).
- **A row of pieces is measured in one go too.** `pieces()` in the spec reads place, size, colour and state of every piece in one `evaluate`; `expectFilledPieces` wants the filled ones to be the first of the document, whatever the direction.
- **A field with the width "fill" changes the columns of its whole form.** Half of the form is 342px in the spec's collection and 293px in a form which has such a field. That field is therefore in a collection of its own (`sandbox_meter_wide`): in the first one it made a text which the older tests count on no longer fit.
- **A field is squeezed by its `.interface`,** not by the `.field` around it, which does not get narrower than about 200px.
- **A resized window goes on settling,** so a test reads a width and a count together and again until they agree (`toPass`, with a time limit: without one it goes on until the test's own).
- **Colours are read from the page, not from the styles.** The computed style of a painted surface is the same gradient everywhere; `pixel()` in the spec takes a screenshot of one pixel and reads it out of the picture, and `colourOf` asks for the middle of an element or a share of its width. The expected colour of a blend or of a faded colour is worked out in the spec, and compared within a few steps of 255.
- **The form hands over `null` before the item arrives,** so a test first waits for the text it expects.
- **The smallest fill is 12px in the form and 8px in the display,** whatever the value. `expectFilled` in the spec knows it; a test of a small share has to as well.
- **Two questions about two boxes are two moments.** The End key and the space bar scroll the page, and the scrolling goes on for a while. `expectFilled` therefore measures the track and its fill in one `evaluate`; asked one after the other, the two were once 19px apart.
- **Right-to-left needs no user, but not the root element either.** The app writes `dir` on the root element again with every update of the document head. The spec's `turn()` sets it on `body`. That works because the meter follows the page and ignores the `direction` it is handed, which stays `ltr` in such a page.
- **An inline block which cuts its content sits on the line by its lower edge,** and so does one which merely holds a block that cuts. The line grows by a pixel or five and the text stands too high beside other text; a table cell of 20px hides it, a display template does not. The test of the related-values template compares the height of the letters.
- **A theme colour can only be read once the page has its theme.** `token()` right after `page.goto` gives the colour of the text, since the variable is not there yet. Read it after the first thing the test waits for.
- **A run of one test recreates the collections,** because `beforeAll` runs for it too. What the test of the emptied options saved is gone after it, so look at that state in a full run or set it through the API.
- **What shows of a text is worked out, not asked.** `shown()` in the spec takes the box of the number and cuts it by every element around it which hides its overflow, up to the cell or the field. A number which has wrapped to the hidden second line still has a box and its text; only that sum says that nothing of it shows.
- **The app's tooltip leaves `data-tooltip` on its element.** The display always has a tooltip now, so its root carries that attribute beside its own.
- **Arabic digits are narrower than western ones in the app's font.** The longest text of the spec fits half the form for an Arabic user and not for an English one; the Arabic test squeezes the field to 150px instead.
- **A test which changes the administrator's language restores it in a `finally`.** Every other test counts on English.
- **The options form of the display has two notices** once the list of thresholds is empty: ours, and "No items" of the list. Find ours by its text.
- **The app's tooltip is one shared element with one timer** (`app/src/directives/tooltip.ts:29-50`). A mouse which arrives while the page is still settling gets none; `expectTooltip` in the spec moves the mouse away and back until the tooltip shows.
- **A collection which points at `sandbox_meter`** stops the spec from dropping it. `sandbox_meter_owner` is dropped first; a collection made by hand to try a template has to be deleted by hand.
- **Playwright's snapshot of the accessibility tree does not print `aria-valuetext`.** The spec reads the attributes.

## Known gaps

- Only Directus 11.17.4 has been tested. The browser tests run in Chromium only; Firefox and WebKit were looked at by hand, a touch device not at all. The form was last looked at in those two before its layout became the stacked one; the display is as it was then.
- The editing was tried in Chromium only, with a mouse and a finger which Playwright moves. A pen and a real touch screen were not tried. The pointer lock is tested in the full Chromium without a window; the owner tried it with a real mouse, where it worked.
- Under the pointer lock `movementX` was only seen at a device pixel ratio of 1.
- Escape ending a pointer lock in the browser's own way was not produced: Playwright's Escape reaches the page as a key. The test ends the lock from the page instead, which the meter cannot tell from it.
- `nonEditable` and `loading` were not seen on their own in a browser, and a user who may only read, and a batch edit, were not tried again since the meter can be edited. All of them reach the meter as `disabled` or as one of those two.
- A big integer beyond 2^53 is written as the nearest number which can be held, as the stock Slider does.
- Not tested with a screen reader. The role, the names and the value attributes were checked through the DOM and the accessibility tree which Playwright reads.
- Not tried next to another extension which registers an interface or a display with the id `meter`.
- `loading` was not seen on its own: the form covers the field with its own placeholder then, and the component does not declare the prop. A content version compared with the main item was not tried; the comparison of two revisions was.
- A form inside the translations interface with a right-to-left language was not tried. The meter there runs in the direction of the page, by decision.
- A database which returns `decimal` and `bigInteger` values as text was not tried: SQLite returns numbers. The unit tests and a field with limits stored as text cover the reading of such text.
- The app at the width of a phone was measured, not seen: at 390px its navigation covers the form in a fresh session.
- The raw value editor and **Clear Value**, the comparison of revisions, a user who may only read, a batch edit, the Arabic and the Hebrew user and the other two browsers were tried by hand only, and in the light theme only.
- Not tried with a custom theme.
- The pieces and the colourings were looked at in Chromium only, and not with forced colours, in a card, in a display template or at the three row heights of the table. The row of pieces is one inline piece where the bar is. `color-mix()` and `:dir()` need a browser of 2023 or later; in an older one a faded colour falls back to the plain track or the primary colour, and a gradient does not turn in a right-to-left page.
- The pieces are counted in pixels of 16 to the rem, and drawn in rem. With another root font size the two would drift apart; the app does not change it.
- No browser test reaches the cap of 200 pieces, which takes bars in a field of a thousand pixels. The unit tests pin it.
- The geometry of the pieces (`pieceGeometry`) is unit-tested but not compared with the page by a test of its own: the browser tests measure the same gaps, sizes and edges piece by piece.
- A width of half a pixel more or less at the moment the count would change was not tried; the count is taken from the observer's size of the border box.
- Packed dots in a field as wide as the form are a short row at the start, with the value text at the far end of the line under them. `spread` is there for that.
- With pieces a value just above the minimum fills nothing, and one just under the maximum everything: only the text tells them from the ends. That is the rounding rule. Without a value, many thin bars are a lattice of dashes rather than outlines.
- A gradient is blended in sRGB by the browser, from stop to stop. In pieces it ignores the gaps: each piece shows an equal part of the scale.
- The dashed outline of a field without a value and the app's placeholder are in subdued colours, about 2 to 1 against the page in the default light theme. Neither is the only carrier of anything: the dash beside the outline is in the text colour.
- A caption of the display cannot be emptied where the interface has one: it is taken over again. A colour or a list of thresholds which was set or emptied in the display does not follow the interface again; only removing the key from the stored options does that, and the options form has no control for it.
- The order of the two pairs of limits follows what the stock Slider of 11.17.4 does with a field which holds both. Another version of Directus may differ; the browser test which reads the Slider's own limits would then fail.
- A text which does not fit is left out without a mark. In the display the tooltip has it; in the form only assistive technology and the raw value of the field do, and the line it would stand on stays empty. In the form that takes a field narrower than the text itself. A column of the default width has room for "100%" and "7 / 12" and not for "35 / 60".
- In a display template the text of the display is one piece: where it does not fit the line it is replaced by the template's ellipsis, in the smallest cards together with the bar.
- The height of the display's text box is `1lh`. The fallback for a browser without that unit, the line height of a table cell, was not tried in such a browser.
- The fraction as plain text (the display's handler) carries no direction mark, so in a right-to-left page the app may lay "7 / 12" out as "12 / 7" where it prints that string.
- "Value Text", "Thresholds", "Value / Maximum", the notes of the options, the notice of the display's options form and the fallback name "Meter" are English only.
